# Концепция vesma-specs

Статус: черновик учредительной сессии (финал — за АрхКомом, см. бриф).
Автор: TL-сессия vesma-cortex, директивы владельца 2026-10-03/04.

## 1. Зачем этот слой существует

До 2026-10-04 экосистема VESMA строила инфраструктуру управления
компонентами ad hoc: пять механизмов запуска сервисов (по инвентарю
учредительного брифа), два уровня systemd-юнитов, конфиги в
легаси-именах, дубль-сервисы. Каждый компонент требовал собственной
обвязки, каждая волна — собственного механизма. Директива владельца
(2026-10-04, «CLI-first» + «супервайзер-архитектура») фиксирует
противоположный принцип:

> CLI `vesma` управляет ВСЕМИ компонентами по единым контрактам; система —
> один супервайзер с дочерними компонентами; падение второстепенного
> компонента = деградация + подсветка + алертинг, но не падение системы.

Чтобы это работало, правила приёма компонентов должны быть **декларативными
и общими** — иначе каждый новый компонент снова потребует дописки CLI.
Этот репозиторий — дом таких правил.

## 2. Что здесь живёт (и что нет)

**Живёт** — всё, что описывает, КАК компоненты соединяются:

- **Интерфейсы**: контракт компонента (манифест), контракт супервайзера
  (запуск/остановка/health/рестарт-политики), контракт контрольного сокета
  (CLI ↔ живой супервайзер), контракты данных между компонентами.
- **Манифесты-примеры**: заполненные образцы для каждого типа компонента
  (в-процесс модуль / внешний процесс / отдельный раннтайм).
- **Конформанс-сьюты**: чеклисты и исполняемые проверки «компонент
  соответствует контракту vN» — гейт интеграции.
- **Канонический лэйаут**: где конфиги, данные, логи, сокеты — для
  user- и system-профилей установки (deb-подобная дисциплина).
- **Глоссарий и карта экосистемы**: какие компоненты существуют, кто
  какой контракт реализует.

**Не живёт** — всё, что фиксирует, ЧТО мы обещали до измерения:
препреги, аддендумы, калибровочные протоколы, вердикты экспериментов
(дом: vesma-canon, append-only доказательный слой). Также не живёт
реализация: код компонентов остаётся в своих репах (vesma, vesma-eyes,
vesma-mesh, vesma-agent, vesma-cortex); здесь — только контракты и их
проверки. Серверные развёртывания (deploy/ движка: helm/docker/podman)
— вне скоупа, кроме контрактов, которые они потребляют.

## 3. Принципы (наследуются из принятых решений)

1. **Contract-first**: контракт = source of truth, реализация следует.
   Семейный прецедент — АрхКом федерации 2026-07-20 (protobuf-контракты
   до реализации).
2. **CLI-драйвность**: ни один компонент не требует дописки CLI — только
   манифест + конформанс (директива владельца «CLI-first»).
3. **Тиры критичности**: обязательное ядро (сервер памяти + API) против
   опциональных компонентов; контракт кодирует тир, супервайзер —
   рестарт-политику и деградацию (прецедент CORTEX-E fail-open).
4. **SemVer + breaking-detector + deprecation-окна**: ломающие изменения
   несут переходный dual-период (прецедент: манифест артефакта schema 2,
   vesma-cortex ADR 0003).
5. **Пример обязателен**: спецификация без примера-минимума не мержится.
6. **Слои разделены**: specs (живые контракты) ≠ canon (запечатанные
   обещания). Правило границы — в README.

## 4. Адресаты

- **Движок vesma** — супервайзер и CLI: потребляет контракт компонента
  и контракт сокета (карточка `cli-service-management` доски vesma).
- **Компоненты экосистемы** — vesma-eyes (Node), vesma-mesh (Go),
  vesma-agent (Go), vesma-board, будущие: заявляют себя манифестом.
- **Внешние интеграторы** (горизонт) — публичные спеки = витрина
  «как подключиться к экосистеме» без чтения кода движка.
- **АрхКом VESMA** — место разрешения споров о форме контрактов;
  вердикты АрхКома фиксируются здесь же рядом со спекой.

## 5. Открытые вопросы учредительной сессии

Полный список — в брифе (§5). Ключевые: форма манифеста (YAML-схема),
семантика health (пассивный порт/endpoint vs active probe), политика
рестартов по тирам, расположение сокета в лэйауте, отношение к
systemd-юнитам (генерация CLI-ем), профиль лэйаута для system-установки.
