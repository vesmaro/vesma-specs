# Бриф учредительной сессии vesma-specs (2026-10-04)

> Первый пункт работы этой сессии — **АрхКом**: проработка архитектуры,
> структуры репозитория и первых контрактов. Этот бриф — вход; он фиксирует
> контекст, уже принятые решения (не переигрывать без владельца) и
> открытые вопросы. Концепция слоя: [concept.md](concept.md).
> Карта: [roadmap.md](roadmap.md).

## 1. Контекст: три директивы владельца за одну неделю

1. **CLI-first (2026-10-04).** Никаких промежуточных sh-обёрток: все
   сценарии управления всеми компонентами — через CLI `vesma`
   (`service install/start/stop/restart/status/logs`). Пакет — как
   deb/rpm: чётко прописанные директории конфигов/данных/логов.
   Инвентарь хаоса на машине владельца (5 механизмов запуска, 2 scope
   юнитов, дубль борды, pkill-паттерны в ExecStop) — в брифе
   `/Project-Vesma/handoff/vesma-cli-service-management-directive-20261004.md`.
2. **Супервайзер-архитектура (2026-10-04).** Один сервис vesma с
   дочерними процессами-компонентами; обязательное ядро vs опциональные
   компоненты; падение опционального = деградация + подсветка + алертинг,
   система жива. Рабочие допущения (владелец не контрсловил): ядро =
   только сервер памяти + API; управление — через контрольный unix-сокет
   (docker-паттерн), socket activation отклонён.
3. **Единый контрактный интерфейс + vesma-specs (2026-10-04).** Утилита
   не дописывается под компонент: компоненты подключаются по контрактам.
   Этот репозиторий создан владельцем для дом этих контрактов
   (vesmaro/vesma-specs, публичный; создан 2026-10-04, founding-доки —
   первый коммит).

## 2. Уже решено (нерушимо без владельца)

- **specs ≠ canon**: два разных репозитория, слои разделены. Правило
  границы: «КАК соединяются → specs; ЧТО обещано до измерения → canon».
  Историю canon не переписывать; живущие версии интеграционных контрактов
  переезжают в specs с указателями (первый кандидат: ADR-0004
  decision-provider, vesma-canon).
- **Дисциплина контрактов**: SemVer, breaking-change-детектор в CI,
  deprecation-окна с dual-поддержкой, пример-минимум обязателен.
- **Лицензия** Apache-2.0 (семейный дефолт). **Язык документов** —
  русский, технические термины EN (канон экосистемы).
- **Миграция прода на ноутбуке владельца** — строго после 2026-10-16
  (B0-окно телеметрии модели; рестарты сегментируют наблюдение). Спеки и
  код CLI писать можно сейчас.
- **Границы треков**: этот репозиторий — контракты; реализация `vesma
  service` живёт в движке (карточка `cli-service-management` доски
  `~/.gcw/tasks/vesma/`, дизайн-база `docs/project/cli-architecture-rework.md`).

## 3. Первый пункт: АрхКом — повестка

Созвать АрхКом VESMA (позиции: архитектор, SRE/DevOps, backend,
безопасность — по канону GCW; протокол в `~/.gcw/architectural-committee/`,
вердикты рядом со спеками). Вопросы:

1. **Репозиторий**: структура каталогов (спека-на-контракт: `specs/<name>/
   vN/{spec.md, schema, examples/, conformance/}`? единый CHANGELOG?);
   где живут вердикты АрхКома; нужен ли `adrs/` внутри specs.
2. **Контракт компонента v1** (ядро всей работы): поля манифеста —
   name/version, kind (in-process | child-process), launch (команда,
   рабочая директория, env), health (endpoint/порт/exit-semantics),
   tier (core | optional), stop-semantics (graceful signal + timeout),
   config-schema (секция общего конфига), ownership/провенанс.
   Формат: YAML-схема + JSON-Schema валидатор + 3 примера-минимума
   (python-модуль, внешний процесс, чужой раннтайм).
3. **Контракт супервайзера**: изоляция (падение ребёнка ≠ падение
   супервайзера), рестарт-политики по тирам (core — всегда с backoff;
   optional — N попыток, затем down+health-флаг+алерт), reaping детей
   (смерть pkill-паттернам), relationship с systemd (ОДИН юнит над
   процессом vesma; в контейнере — PID 1; генерация юнита CLI-ем).
4. **Контракт контрольного сокета**: путь в лэйауте, протокол
   (статус/логи/старт/стоп по манифестам), права доступа (0600, user
   scope vs system scope), аутентификация локального сокета.
5. **Канонический лэйаут** (deb-подобный): user-профиль
   (`~/.config/vesma/`, `~/.local/share/vesma/<component>/`,
   `~/.local/state/vesma/`, `~/.cache/vesma/`); нужен ли system-профиль
   (`/etc/vesma`, `/var/lib/vesma`) и когда; venv-дисциплина (один
   управляемый venv на компонент внутри лэйаута, PYTHONNOUSERSITE=1,
   doctor-проверки перекрытий — боль владельца с venv).
6. **Conformance**: как исполняется проверка соответствия (отдельный
   раннер? pytest-пак? кто его держит — движок или specs); гейт интеграции
   компонента в экосистему.
7. **Governance репозитория**: кто мержит спеки (TL+АрхКом?), как
   фиксируются вердикты, как спека объявляется устаревшей.

## 5. Открытые вопросы к АрхКому (из концепции §5)

Форма манифеста и валидация; семантика health (пассивная декларация vs
active probe — для in-process модулей endpoint'а нет, нужен договорённый
интерфейс); политика рестартов: числа/окна; сокет: имя и место в лэйауте;
systemd: генерирует CLI или пишет оператор; system-профиль лэйаута —
нужен ли в горизонте v1; i18n спек (EN для внешних? RU-канон?);
conformance-раннер: чей пакет.

## 6. Ограничения и гигиена

- Секреты хоста: `~/.secrets/` (имена в глобальных правилах); в спеках
  и примерах — никогда.
- Пуши в org — по SSH (canon: API мутации org — только curl+Bearer
  `gh_token_vesmaro`; `gh`-клиент даёт 404-ghost).
- Коммиты: английские (`type(scope): description`); проза документов —
  русская.
- G1–G4 mnemo-гейты обязательны (канон vesma integration pack).
- Не трогать чужие репы (vesma, eyes, mesh, agent) из этой сессии —
  только спецификации и кросс-ссылки issues.
