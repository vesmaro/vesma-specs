# service-lifecycle v1 — контракт супервайзера

Ключевые слова MUST / MUST NOT / SHOULD / MAY интерпретируются по RFC 2119.
Проза — русская; идентификаторы, директивы и значения полей — английские.

## 1. Scope

Этот контракт определяет поведение **супервайзера** — единственного
долгоживущего процесса `vesma`, который владеет жизненным циклом всех
компонентов экосистемы на машине: запуск, health, рестарт, остановка,
наблюдаемость.

**В скоупе:**

- модель процессов (сессии, группы, reaping, PID1-режим);
- изоляция: падение ребёнка ≠ падение супервайзера и контрольного сокета;
- FSM ребёнка и таблица переходов;
- структурные строки наблюдаемости (фиксированный формат);
- рестарт-политики по тирам (core / optional) с контрактными числами;
- порядок старта и graceful-остановки (топологический / реверс-топологический);
- ровно один systemd-юнит над процессом vesma: шаблон + hardening-блок;
- threat model (мини-STRIDE) и миграция с легаси-механизмов запуска.

**Вне скоупа (домены соседних контрактов):**

- форма и поля манифеста компонента — `specs/component-manifest/v1`
  (манифест = вход супервайзера; супервайзер потребляет, не определяет);
- протокол CLI ↔ живой супервайзер — `specs/control-socket/v1`;
- канонические пути (конфиги, state, cache, data, сокет) — `specs/layout/v1`;
- семантика health-проб конкретного компонента — health-секция его манифеста;
- серверные развёртывания (контейнерные/оркестраторные профили) — трек движка.

Супервайзер реализуется движком `vesma` (карточка `cli-service-management`);
этот контракт — источник требований и гейт conformance-проверок.

## 2. Терминология

| Термин | Значение |
|---|---|
| супервайзер | процесс `vesma`, владеющий жизненным циклом компонентов; в in-process режиме совмещает ядро (сервер памяти + API) |
| ребёнок (child) | дочерний процесс компонента, заспавненный супервайзером по launch-манифесту |
| компонент | единица экосистемы, заявленная манифестом (`specs/component-manifest/v1`); in-process компонент живёт в процессе супервайзера, child-process — отдельным процессом |
| tier | тир критичности: `core` (обязательное ядро) или `optional` |
| FSM | конечный автомат ребёнка: `stopped → starting → healthy → degraded → backoff → stopped`, плюс `blocked` |
| health-проход | один успешный результат health-проверки из манифеста компонента |
| «up» | состояние компонента = первый успешный health-проход после spawn |
| backoff | пауза перед следующей рестарт-попыткой (экспоненциальная, с jitter) |
| crash-loop | серия рестартов без достижения healthy; для core — 10 попыток |
| grace period | окно между SIGTERM и SIGKILL при остановке (из stop-семантики манифеста) |
| pgid | идентификатор группы процессов; у ребёнка pgid == pid (setsid) |
| subreaper | процесс с `prctl(PR_SET_CHILD_SUBREAPER, 1)`: осиротевшие потомки репарентятся в него |
| lazy-retry | редкая фоновая рестарт-попытка без алерт-спама (для optional после исчерпания бюджета) |
| контрольный сокет | unix-сокет управления живым супервайзером (`specs/control-socket/v1`) |
| юнит | сгенерированный systemd unit `vesma.service` (user- или system-профиль) |

## 3. Контракт

### 3.1 Модель процессов

**Сессии и группы.** Каждый ребёнок стартуется с `start_new_session=True`
(setsid): pgid ребёнка == его pid. Следствие: ребёнок и все его потомки
образуют одну POSIX-сессию, адресуемую одним числом. Остановка компонента —
`kill(-pgid, …)` по группе. **Инвентаризация процессов по имени (pkill)
запрещена и не нужна по построению** — антипаттерн инвентаря хаоса
(убийство чужих процессов по шаблону имени) исчезает конструктивно.

**Граница групповых сигналов (MUST).** `kill(-pgid, …)` допустим ТОЛЬКО
пока прямой ребёнок не reaped: unreaped-зомби удерживает pid/pgid от
переиспользования ядром. После reap группы ребёнка групповые сигналы
ЗАПРЕЩЕНЫ — открыто окно pgid-reuse (номер группы уже может быть выдан
новому процессу).

**Reaping.** SIGCHLD → цикл `os.waitpid(-1, WNOHANG)` до исчерпания
(ECHILD). Ни один завершившийся ребёнок не остаётся зомби.

**Subreaper.** MUST: супервайзер устанавливает
`prctl(PR_SET_CHILD_SUBREAPER, 1)`. Осиротевшие внуки (потомки детей,
пережившие родителя) репарентятся в супервайзер и reap'ятся им — зомби
не оседают в init и не теряются из-под контроля.

**PID1-режим (контейнер).** Тот же бинарник; супервайзер принимает роль
PID 1 контейнера. MUST: обязательные обработчики SIGTERM/SIGINT; reap
всех осиротевших; graceful-стоп детей ДО exit. Conformance-кейс:
«PID1 reap'ит осиротевшего внука».

**In-process ядро.** Сервер памяти + API — in-process компонент,
живущий в процессе супервайзера. Смерть in-process ядра = смерть
супервайзера → рестарт юнита systemd. Fail-fast покрывается естественно;
отдельный механизм рестарта ядра НЕ вводится — зафиксировано сознательно.

### 3.2 Изоляция (MUST)

1. Падение ЛЮБОГО подмножества детей оставляет супервайзер и контрольный
   сокет живыми (кроме `kind: in-process`: смерть in-process модуля = смерть
   супервайзера, §3.1). Доступность управления (status/stop/logs) —
   инвариант, а не привилегия «здорового дня».
2. Исключение в per-child коде ловится на границе (FSM ребёнка → backoff);
   main loop не умирает никогда. Никакой путь исполнения per-child логики
   не выводит супервайзер из цикла.
3. Дети не получают fd контрольного сокета и путь к нему в env
   (обоснование — threat model, §7).
4. Дети не доверяют друг другу: IPC — только через явные контракты API.
   Супервайзер не строит скрытых каналов «ребёнок → ребёнок».
5. **Env ребёнка** = конструируемый PATH + `env.vars` манифеста + содержимое
   `env_file`. PATH конструируется по канону: `{venv_bin}`-каталог компонента
   (для python-детей) + фиксированная строка
   `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`; переменная
   `PATH` в `launch.env.vars` ЗАПРЕЩЕНА (отклоняется валидацией — конфликт с
   конструируемым PATH недопустим). Семантика `env -i` мандатна: ни одна
   хостовая переменная не протекает в ребёнка, кроме перечисленного — урок
   «401-шторма» протекания хостового env. Conformance: ребёнок печатает своё
   окружение, раннер сверяет allow-list'ом (SL-13).

**In-process модули (MUST).** In-process модуль = trust-equivalent
супервайзера: исполняется в его процессе, со всеми его fd и env. Подключение
in-process модулей — только first-party код; сторонний код — только
child-process.

**Единый trust-domain v1 (MUST — фиксация реальной границы).** Все дети
исполняются в одном systemd-юните под одним uid. Межкомпонентная файловая и
env-изоляция в v1 НЕ обеспечивается: same-uid ребёнок может читать env-файлы
соседей через файловую систему и `/proc/*/environ`, писать в чужие
data-каталоги. Это осознанное ограничение v1; горизонт v2 — per-child sandbox
и разделение uid (system-профиль, `specs/layout/v1` §3.3). Пункты 1–5 выше —
изоляция надёжности и управления (supervision), а не межкомпонентная
безопасность same-uid среды.

### 3.3 FSM ребёнка

Состояния: `stopped → starting → healthy → degraded → backoff → stopped`,
плюс `blocked` (для зависимых при неподнятой core-зависимости).

Таблица переходов (нормативна; запрещённые переходы реализация не должна
допускать — SL-07):

| # | from | событие | to | Норма |
|---|---|---|---|---|
| T1 | stopped | spawn ребёнка (старт, рестарт, lazy-retry, ручной start) | starting | MUST |
| T2 | stopped | start-запрос при неподнятой core-зависимости | blocked | MUST |
| T3 | blocked | core-зависимость достигла healthy | starting | MUST |
| T4 | starting | первый успешный health-проход | healthy | MUST (определение «up») |
| T5 | starting | exit процесса до healthy | backoff | MUST (рестарт-политика тира, §3.5) |
| T6 | starting | ручной stop / остановка супервайзера | stopped | MUST |
| T7 | healthy | health-пробы проваливаются (порог деградации из манифеста) | degraded | MUST |
| T8 | healthy | exit процесса при живом рестарт-бюджете | backoff | MUST |
| T9 | degraded | восстановление health-прохода | healthy | MUST (recovery) |
| T10 | degraded | exit процесса при живом бюджете | backoff | MUST |
| T11 | degraded | exit при исчерпанном бюджете (optional) | degraded | MUST (терминальное состояние деградации) |
| T12 | backoff | истечение backoff-таймера → respawn | starting | MUST |
| T13 | backoff | ручной stop / остановка супервайзера | stopped | MUST |
| T14 | любой | graceful shutdown супервайзера | stopped | MUST (реверс-топологический порядок, §3.5) |

Примечания:

- Глобальный health супервайзера — отдельный флаг уровня супервайзера,
  не состояние FSM: core crash-loop опускает глобальный health в
  `degraded`, продолжая цикл backoff/starting у самого ребёнка.
- Порог деградации (T7) и health-механика конкретного компонента — домен
  health-секции его манифеста (`specs/component-manifest/v1`).

### 3.4 Наблюдаемость — часть контракта

Каждая единица жизненного цикла публикует **ровно одну фиксированную
структурную строку**. Формат (грамматика, нормативна — SL-08):

```
vesma.supervisor component=<name> event=<spawn|exit|health|degraded> pid=<n|none> [<key>=<value> ...]
```

Имена компонентов и значения полей — токены `[a-z0-9_.-]`, без пробелов
и кавычек; дополнительные поля MAY добавляться после обязательных, не
ломая префикс и порядок обязательных.

| event | Обязательные доп. поля (в этом порядке) | Семантика |
|---|---|---|
| `spawn` | — (MAY: `attempt=<n>`) | ребёнок заспавнен; `pid` — новый pid |
| `exit` | `code=<n\|none> signal=<NAME\|none>` | ровно одно поле несёт значение: умер по коду → `code=<n> signal=none`; по сигналу → `code=none signal=<NAME>` (без префикса `SIG`) |
| `health` | `from=<state> to=<state>` | переход FSM по T4/T7/T9 |
| `degraded` | `state=degraded reason=<token> attempts=<n> window=<Ns\|none>` | supervisor-level деградация: `reason=restart-budget-exhausted` (optional) или `reason=crash-loop` (core); `pid` — последний заспавненный инстанс |

Уровни серьёзности: `spawn`/`health` — INFO; `exit` с кодом 0 — INFO,
с ненулевым кодом или сигналом — WARNING; `degraded` — ERROR.

`pid` на `degraded`-строке — последний pid инстанса компонента; если
инстанс ни разу не спавнился — `pid=none` (пояснение кодификации: в тексте
вердикта строка optional-деградации процитирована без префикса и pid;
канонический префикс `vesma.supervisor` и `pid` присутствуют всегда).

**Журнал history/ (MUST).** Каждый переход FSM каждого компонента и каждое
изменение глобального health супервайзера дополнительно записываются в
журнал супервайзера `~/.local/state/vesma/history/` — append-only; формат
записей — те же структурные строки этого параграфа с ISO-8601 timestamp.
Append-only здесь — семантика супервайзера (единственный писатель);
файловых гарантий против same-uid записи нет — принято в v1, sandbox —
в v2 (§3.2, единый trust-domain). Путь, права и append-only семантика
журнала — `specs/layout/v1`.

**Строки детей в journald.** Супервайзер маркирует строки детей
`SYSLOG_IDENTIFIER=vesma-<component>` при пересылке в journald (маркировку
выполняет супервайзер, не ребёнок). `vesma service logs --component=X` =
journalctl-фильтр по идентификатору, не grep по каше.

### 3.5 Рестарт-политики

Числа ниже — **контрактные дефолты**. Манифест MAY переопределить через
`restart.*` в клампах: `base` ≥ 500ms, `max` ≤ 5min, `attempts` ≥ 3
(клампы проверяются install-валидацией, SL-18).

**core** — рестарт бесконечно:

- экспоненциальный backoff: base 1s, ×2, cap 30s, jitter ±20%;
- счётчик сбрасывается после 300s непрерывного uptime;
- crash-loop: 10 попыток без достижения healthy → глобальный health =
  `degraded` + алерт-строка (§3.4, `reason=crash-loop attempts=10 window=none`);
  рестарт продолжается — супервайзер жив.

**optional** — бюджетная дисциплина:

- максимум 5 попыток за окно 300s;
- исчерпано → состояние `degraded` + health-флаг + **РОВНО ОДНА**
  структурная ERROR-строка:
  `vesma.supervisor component=<name> event=degraded pid=<n> state=degraded reason=restart-budget-exhausted attempts=5 window=300s`;
- далее lazy-retry раз в 300s **без алерт-спама** (последующие попытки и
  их исходы — INFO, новые ERROR-строки не публикуются);
- ручной `vesma service start --component=X` сбрасывает бюджет.

**In-process ядро**: смерть in-process ядра (сервер памяти + API) = смерть
супервайзера → рестарт юнита systemd (см. §3.1).

**Порядок старта.** Топологический по `depends_on` (цикл = ошибка
install-валидации); независимые компоненты стартуют параллельно.
«up» = первый успешный health-проход (T4). Core-зависимость не поднялась →
зависимые ждут бесконечно с backoff-логами (FSM: `blocked`, T2/T3) —
ограниченного таймаута ожидания core-зависимости нет.

**Остановка.** SIGTERM супервайзеру (дефолтный сигнал systemd — см. §3.6)
→ реверс-топологический порядок: зависимые останавливаются раньше
зависимостей. Каждый ребёнок: `kill(-pgid, SIGTERM)` в рамках grace period
(из stop-семантики манифеста) → по истечении — `kill(-pgid, SIGKILL)`
группы. Суммарный внутренний бюджет остановки детей проектируется
строго меньше `TimeoutStopSec` юнита (запас ≥ 25%). Выход супервайзера —
только после reaping всех детей (PID1-режим: то же до exit).

### 3.6 systemd: ровно один юнит

systemd управляет **ровно одним** юнитом над процессом `vesma`;
**systemd НИКОГДА не знает о детях** (контрактная формулировка): ни в
директивах юнита, ни в stop-логике systemd нет упоминаний компонентов —
весь порядок остановки детей — ответственность супервайзера. Юнит
**НИКОГДА не содержит argv компонентов**: `ExecStart` = статическая строка
запуска супервайзера (`<venv>/bin/vesma service run`); spawn детей — только
execve-массивом из `launch.argv` манифеста. Юнит генерирует
`vesma service install` (user-профиль:
`~/.config/systemd/user/vesma.service`).

**Шаблон юнита (таблица MUST — SL-17):**

| Директива | Значение | Обоснование |
|---|---|---|
| `Type=` | `exec` | старт считается удавшимся только после успешного `exec()`; ошибка запуска = провал юнита |
| `ExecStart=` | статическая строка запуска супервайзера: `<venv>/bin/vesma service run` (одна строка, **без `sh -c`**) | юнит НИКОГДА не содержит argv компонентов: spawn детей — execve-массивом из `launch.argv` манифеста; shell-конкатенация — легаси-антипаттерн |
| `ExecStop=` | **НЕ генерируется** | дефолтный SIGTERM главному = контрактная остановка (§3.5); pkill-антипаттерн исчезает |
| `KillSignal=` | `SIGTERM` | совпадает с контрактной остановкой |
| `KillMode=` | `mixed` | SIGTERM главному → упорядоченный graceful stop детей силами супервайзера; по `TimeoutStopSec` systemd SIGKILLит весь cgroup как backstop |
| `TimeoutStopSec=` | `90` | внутренний бюджет стопа детей + запас |
| `Restart=` | `on-failure` | смерть супервайзера (в т.ч. in-process ядра) → рестарт юнита |
| `RestartSec=` | `5s` | пауза между рестартами юнита |
| `StartLimitIntervalSec=` | `300` | окно детекта штатного crash-loop юнита |
| `StartLimitBurst=` | `5` | порог: 5 провалов за 300s → юнит встаёт (fail-fast наружу, не вечный цикл) |
| `StandardOutput=` | `journal` | всё в journald |
| `StandardError=` | `journal` | всё в journald |

Маркировка `SYSLOG_IDENTIFIER=vesma-<component>` выполняется супервайзером
при пересылке строк детей (§3.4) — на уровне юнита не выражается.

**WatchdogSec / sd_notify — v2** (осознанно отложено).

| Директива | Значение | Примечание |
|---|---|---|
| `NoNewPrivileges=` | `true` | запрет эскалации через setuid/sgid |
| `ProtectSystem=` | `strict` | вся ФС read-only, кроме `ReadWritePaths` |

Закрывает вектор «компрометация optional-компонента → запись в venv движка → код супервайзера при рестарте юнита»; doctor — DR-12 (`specs/layout/v1` §3.10) |
| `ProtectHome=` | `read-only` (user) / `true` (system) | home недоступен на запись (user) / скрыт (system) |
| `PrivateTmp=` | `yes` | изолированный /tmp |
| `PrivateDevices=` | `yes` | без доступа к устройствам |
| `ProtectKernelTunables=` | `yes` | без записи в /proc/sys |
| `ProtectKernelModules=` | `yes` | без загрузки модулей |
| `ProtectKernelLogs=` | `yes` | без доступа к kernel log |
| `ProtectControlGroups=` | `yes` | без записи в cgroup-иерархию |
| `RestrictSUIDSGID=` | `yes` | запрет создания suid/sgid-файлов |
| `LockPersonality=` | `yes` | фиксация personality |
| `RestrictRealtime=` | `yes` | без RT-планирования |
| `CapabilityBoundingSet=` | пусто | никаких capabilities |
| `RestrictAddressFamilies=` | `AF_UNIX AF_NETLINK AF_INET AF_INET6` | остальные семейства сокетов запрещены |
| `SystemCallFilter=` | `@system-service` | **Tier B**: активируется после smoke-матрицы bare/distrobox/podman; до этого генератор MAY печатать строку закомментированной с громкой пометкой |

`MemoryDenyWriteExecute` — **исключён ОСОЗНАННО**: он ломает CPython
native extensions (JIT/WX-память в нативных модулях); включение означало бы
неработающий супервайзер ради галочки — зафиксировано здесь, чтобы
«безопасностный аудит» не вернул директиву молча.

**Контейнеры.** В контейнерах допустим ТОЛЬКО ГРОМКИЙ задокументированный
даунгрейд filesystem-директив — `ProtectSystem`, `ProtectHome`,
`ReadOnlyPaths`, `ReadWritePaths`, `PrivateTmp` (не применимых без
реального systemd-хоста): печатается в install-выводе и виден в
`vesma service status`. Даунгрейду подлежат ТОЛЬКО эти директивы: попытка
даунгрейда иной директивы hardening-блока = ошибка генерации юнита. Тихих
деградаций нет (doctor — DR-13, `specs/layout/v1` §3.10).

### 3.7 Коды ошибок — не применимо

Контракт не определяет протокольных кодов ошибок: ошибки жизненного цикла
выражаются FSM-состояниями (§3.3) и структурными строками наблюдаемости
(§3.4). Протокольные коды управления живым супервайзером — дом
`specs/control-socket/v1` (§4.6).

  контракта).

## 7. Threat model (мини-STRIDE)

Супервайзер — **trust boundary**: он владеет окружением, сигнальным
пространством и журналом всех компонентов.

**Ассеты:** процессы детей; env детей; контрольный сокет; cgroup.

**Границы:** (1) супервайзер ↔ дети (spawn, env, fd-наследование, сигналы,
reap); (2) systemd ↔ супервайзер (юнит, cgroup, KillMode); (3) оператор/CLI
↔ контрольный сокет — граница домена `specs/control-socket/v1`.

| Категория | Угроза | Митигация | Проверка |
|---|---|---|---|
| **S**poofing | сторонний локальный процесс представляется CLI/компонентом и подключается к контрольному сокету | права сокета 0600 + peer-credentials проверка (домен `control-socket/v1`); дети без дескрипторов доступа к сокету | SL-14 + операционный контроль прав лэйаута |
| **S**poofing | ребёнок подделывает атрибуцию строк журнала (пишет под чужим идентификатором) | `SYSLOG_IDENTIFIER` выставляет супервайзер при пересылке; ребёнок в journal напрямую не пишет | SL-08; операционный контроль |
| **T**ampering | подмена артефакта запуска между install и spawn | `artifact_sha256` из манифеста проверяется при spawn | SL-18 (клампы/валидация); манифестный conformance |
| **T**ampering | ручная правка сгенерированного юнита (тихое ослабление hardening) | юнит — сгенерированный артефакт («generated, do not edit»); регенерация `install` перезаписывает | SL-17; операционный контроль |
| **R**epudiation | «кто убил компонент?» — нет доказуемой истории | структурные строки exit с `pid/code/signal` + spawn/health/degraded в append-only journald | SL-08 |
| **I**nformation Disclosure | протекание хостового env в детей (401-шторм) | семантика `env -i` мандатна: env = PATH + `env.vars` + `env_file` | SL-13 (ребёнок печатает env, раннер сверяет allow-list) |
| **I**nformation Disclosure | утечка fd/пути контрольного сокета в детей | fd не наследуется, путь отсутствует в env ребёнка | SL-14 (`/proc/<pid>/fd` + env) |
| **I**nformation Disclosure | секреты в строках детей попадают в журнал | компонентные контракты запрещают печатать секреты; супервайзер содержимое не фильтрует (redaction — v2) | операционный контроль |
| **D**enial of Service | зомби-процессы копятся и истощают таблицу процессов | subreaper + `waitpid(-1, WNOHANG)`-цикл | SL-05 |
| **D**enial of Service | застрявший ребёнок блокирует остановку | grace period → SIGKILL группы; `TimeoutStopSec=90` как systemd-backstop | SL-04, SL-16 |
| **D**enial of Service | ребёнок монополизирует CPU/RAM | общий cgroup юнита ограничивает blast radius юзер-профиля; per-component лимиты — v2 | операционный контроль |
| **E**levation of Privilege | ребёнок пытается достать контрольный сокет | fd не наследуется; пути нет в env; peer-check на сокете | SL-14 |
| **E**levation of Privilege | эскалация через setuid/запись в системные пути | `NoNewPrivileges=true`, `CapabilityBoundingSet=` (пусто), `ProtectSystem=strict` | SL-18 |
| **E**levation of Privilege | ребёнок выходит на kernel-поверхности | `ProtectKernel*`, `PrivateDevices`, `RestrictAddressFamilies` | SL-18 |

Каждая митигация закрыта conformance-чеком либо помечена «операционный
контроль» (права файлов, регламент, ревью) — тихих непроверяемых обещаний нет.

## 8. Миграция с легаси

Юниты с pkill-ExecStop и `sh -c`-ExecStart **заменяются генерацией**:
`vesma service install` создаёт новый юнит по §3.6; старые юниты
выводятся из оборота (disable + stop) — ручной перенос директив не
предусмотрен, точка миграции одна: генератор.

| Легаси-паттерн (инвентарь 2026-10-04) | Контрактный ответ |
|---|---|
| 5 механизмов запуска (sh-обёртки distrobox, podman exec, host-нативные бинарники, nohup/& , cron) | один супервайзер: запуск компонента = spawn по манифесту (§3.1) |
| pkill-паттерны в ExecStop (инвентаризация по имени) | `kill(-pgid, …)` по построению; ExecStop не генерируется вовсе (§3.6) |
| `env -i` в sh-обёртке (ручная гигиена окружения на каждый компонент) | `env -i` семантика супервайзера мандатна, конструируется централизованно (§3.2) |
| `sh -c "…"` с конкатенацией в ExecStart | ExecStart = статическая строка запуска супервайзера; argv детей — execve-массивом из launch-манифестов (§3.6) |
| 2 scope юнитов, дубль-сервисы (board ×2) | ровно один юнит над процессом vesma; systemd НИКОГДА не знает о детях; дубль = ошибка install-валидации (§3.6) |
| grep по каше логов | `SYSLOG_IDENTIFIER=vesma-<component>`; `vesma service logs --component=X` = journalctl-фильтр (§3.4) |

Миграция легаси-развёртывания — не ранее закрытия первого окна наблюдения
учредительного трека (founding context — см. `docs/`; рестарты
сегментируют наблюдение) — roadmap фаза 3, трек движка. Спеки и код CLI
этому окну не подчиняются.

**Историческая справка.** Спека намеренно генерифицирована (решение
владельца 2026-10-04): конкретика учредительного окружения — легаси-имена,
целевая машина, детали первого окна наблюдения — сохранена в founding-паке
`docs/` (в частности, бриф директивы
`docs/brief-2026-10-04-archcom-founding.md`) и в истории репы; для
связности истории читай их вместе с этой спекой.
