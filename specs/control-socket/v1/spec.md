# Контрольный сокет супервайзера — `control-socket` v1

> **Статус: draft.** Спека ратифицируется первой реализацией в движке
> `vesma` (карточка `cli-service-management`). Форма контракта — пути и
> права, TOCTOU-процедура, протокол, методы, коды ошибок, лимиты, threat
> model — ратифицирована учредительным АрхКомом VESMA 2026-10-04
> (ADR-0001) и здесь **кодифицируется, а не переигрывается**. Дальнейшие
> изменения — только через SemVer-процесс (§ 8).

Ключевые слова MUST, MUST NOT, SHOULD, SHOULD NOT, MAY трактуются по
RFC 2119. Проза документов — русская; идентификаторы, имена методов и
значения полей — EN (канон экосистемы).

**Паттерн:** docker CLI ↔ dockerd. CLI `vesma` — тонкий клиент к живому
супервайзеру через unix-сокет; супервайзер — единственный держатель правды
о состоянии компонентов (не угадывание по процессам).

## 1. Scope

### 1.1 В скоупе v1

- Канал управления «клиент ↔ супервайзер» по `AF_UNIX`, `SOCK_STREAM`.
- User-профиль установки — единственный реализуемый в v1 (включая
  fallback-путь при пустом `XDG_RUNTIME_DIR`).
- Протокол JSON Lines; методы `hello`, `status`, `start`, `stop`,
  `restart`, `logs`, `health`.
- Модель аутентификации «файловая система = аутентификация» +
  `SO_PEERCRED` как defense-in-depth.
- Коды ошибок, лимиты, мини-STRIDE threat model, conformance-чеклист.

### 1.2 Вне скоупа v1

- **Method-level ACL** — v2, при появлении дистанцированного оператора
  (примечание A к таблице § 3).
- **TCP и любой сетевой транспорт control plane — ЗАПРЕЩЁН** by
  construction (§ 4.7).
- **BSD/macOS** (`getpeereid`) — отдельное решение, вне v1; скоуп v1 явно
  Linux-only.
- **FSM-состояния, health-агрегация, рестарт-политики, тайминги stop** —
  дом [specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md);
  сокет переносит их как непрозрачные строковые значения.
- **Общий лэйаут** (конфиги, данные, кэш, venv) — дом
  [specs/layout/v1](../../layout/v1/spec.md); здесь фиксируются только
  пути и права сокет-каталогов.
- Реализация супервайзера (изоляция детей, reaping) — движок `vesma`.

### 1.3 Отклонённые альтернативы (зафиксировано АрхКомом, не переигрывать)

- **Socket activation** (systemd `.socket`-юнит: сокет создаётся до
  процесса) — отклонён владельцем 2026-10-04. Это сокет **управления**,
  не activation: супервайзер сам владеет путём и сам выполняет
  probe/bind/unlink (§ 4.2). Вернуться к обсуждению только при появлении
  реального сценария (например, управление до инициализации супервайзера).
- **JSON-RPC 2.0** как протокол — отклонён комитетом: notifications,
  batch и его реестр кодов не нужны. Envelope сознательно оставлен
  совместимым по форме (`id`/`result`/`error`), чтобы будущий мост был
  дёшев (§ 8).

## 2. Терминология

| Термин | Значение |
|---|---|
| супервайзер | процесс `vesma`, держатель сокета и родитель компонентов; контракт супервайзера — [specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md) |
| компонент | дочерняя единица экосистемы, заявленная манифестом ([specs/component-manifest/v1](../../component-manifest/v1/spec.md)) |

| FSM-состояние | состояние компонента по [specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md) |

| control plane | совокупность каналов управления супервайзером |

## 3. Пути и права (MUST)

| Профиль | Каталог сокета | Сокет | Аутентификация |
|---|---|---|---|
| **user (v1)** | `${XDG_RUNTIME_DIR}/vesma/`, режим 0700 | `control.sock`, режим 0600 | DAC: владелец каталога; `SO_PEERCRED` defense-in-depth: peer uid == владелец сокета, иначе immediate close |
| **user fallback** | `~/.local/state/vesma/run/`, режим 0700, + WARN в лог (применяется, когда `XDG_RUNTIME_DIR` пуст) | `control.sock`, режим 0600 | то же + обязательная stale-процедура (§ 4.2) |
| **system** (горизонт v2: определяется в спеке, реализация отложена) | `/run/vesma/`, режим 0750, `root:vesma-oper` | `control.sock`, режим 0660 | `SO_PEERCRED` на КАЖДЫЙ accept: uid=root или gid=vesma-oper, иначе deny + audit-строка |

Примечания (MUST):

- **A. Файловая система = аутентификация.** Токены поверх сокета не нужны
  в v1: класс атакующего не меняется — кто может подключиться, может и
  убить процесс той же учёткой. Method-level ACL — v2, при появлении
  дистанцированного оператора (system-профиль).
- **B. Права сокета MUST NOT зависеть от umask.** После `bind` права
  выставляются явно (`chmod`) и проверяются `fstat` (§ 4.2, шаг 5).
- **C. Linux-only.** Скоуп v1 фиксируется явно; BSD/macOS (`getpeereid`) —
  отдельное решение за пределами этой версии.
- **D. Группа `vesma-oper` инсталлятором по умолчанию НЕ создаётся** —
  группа = оператор-эквивалент (урок docker-сокета: членство в группе
  docker эквивалентно root). Группа только документируется; её создание —
  осознанное действие оператора на горизонте v2.
- Проверку peer uid/gid супервайзер выполняет на КАЖДОМ accept, до чтения
  любых данных из соединения.

## 4. Контракт

### 4.1 Pre-flight клиента (защита от lax-хоумдиров) — MUST

При подключении CLI (и любая клиентская реализация SHOULD вести себя так
же) отказывается работать, если каталог сокета:

- группо-записываемый, либо
- миро-записываемый, либо
- принадлежит не текущему пользователю.

При отказе клиент печатает готовую команду исправления с реальным путём
(например `chmod 0700 /run/user/1000/vesma`), но НЕ исполняет её
автоматически. Супервайзер на bind-стороне SHOULD выполнять ту же проверку
перед созданием каталога/сокета (симметричное усиление той же угрозы).

### 4.2 Bind-сторона: TOCTOU/SYMLINK-процедура — MUST

Супервайзер при старте выполняет процедуру строго в этом порядке:

1. **Целевой путь** — по профилю из § 3 (user-профиль: каталог из
   `XDG_RUNTIME_DIR`; он пуст → fallback-путь + WARN-строка в лог).
2. **`bind` по целевому пути.** Успех → шаг 5. `EADDRINUSE` →
   **`connect()`-probe живого**:
   - живой инстанс ответил (connect прошёл и на hello получен валидный
     ответ в пределах таймаута ответа) → **exit «already running»**
     (single-instance guard): не unlink'ать, не bind'ить;
   - `ECONNREFUSED`/`ENOENT` → путь stale → шаг 3;
   - иная ошибка (`EACCES`, `ELOOP`, ...) → отказ старта с диагностикой,
     ничего не удалять.
3. **Перед unlink — `lstat`**:
   - удалять ТОЛЬКО socket-файл своего владельца (`S_ISSOCK` и
     `st_uid == geteuid()` текущего процесса);
   - путь — symlink → **отказ старта + алерт, НИКОГДА не follow**;
   - не-сокет (обычный файл, каталог) или чужой владелец → отказ старта +
     алерт; чужие объекты не удалять.
4. **`unlink` + повторный `bind` + `listen`** по целевому пути. Цикл
   «bind → EADDRINUSE → probe → lstat → unlink → retry bind» — не более 3
   попыток; исчерпаны → отказ старта с диагностикой. Между probe и unlink
   каталог держится под своим владением (`0700`): гонка между ЧУЖИМИ
   супервайзерами невозможна по построению (чужой uid не владеет
   каталогом), а два старта ОДНОГО супервайзера разносит single-instance
   guard (шаг 2: живой probe → exit).
5. **После bind — `fstat` bound-fd**: проверить режим и владельца
   (user-профиль: 0600 и свой uid; см. примечание B к § 3). Расхождение →
   fatal при старте.
6. **Слепой `unlink` живого сокета запрещён контрактом.** Probe перед
   unlink обязателен для всех профилей; для user fallback
   (`~/.local/state/...` переживает перезагрузки) stale-сценарий — норма,
   процедура обязательна на каждом старте.

### 4.3 Протокол (envelope) — MUST

- Транспорт: `AF_UNIX`, `SOCK_STREAM`, UTF-8.
- Кадрирование: **JSON Lines** — одна строка = один запрос, разделитель
  `\n`; одна строка = один ответ (исключение — поток `logs follow`,
  § 4.5).
- Запрос: `{"id": N, "method": "...", "params": {...}}`; `params`
  опционален (отсутствует → трактуется как `{}`).
- Ответ: ровно одно из
  `{"id": N, "result": {...}}` или
  `{"id": N, "error": {"code": N, "message": "...", "data": {...}}}`;
  `data` опционален.
- `id` — целое, генерируется клиентом; сервер возвращает его без изменения.
- Batch и notifications отсутствуют (отклонены с JSON-RPC 2.0, § 1.3).

### 4.4 `hello` и версионирование — MUST

`hello` — ОБЯЗАТЕЛЬНЫЙ первый запрос каждого клиента на каждом соединении.
Любой другой метод до `hello` → error 4 `version_unsupported` с
`data: {"reason": "hello_required", "supported": [<поддерживаемые мажоры>]}`.
Обоснование: до `hello` версия протокола не согласована, поэтому сервер
обязан отказывать по той же ветке, что и при несовпадении major; путь
восстановления един — отправить `hello` (клиент после такой ошибки
продолжает сессию как обычно).

- Запрос: `{"id": N, "method": "hello", "params": {"protocol_version": 1}}`
  — `protocol_version` обязателен.
- Сервер сравнивает **major** версии клиента со своей. Несовпадение major →
  error 4 `version_unsupported`, в `data.supported` — поддерживаемые мажоры.
- Ответ при успехе:

```json
{"id": N, "result": {"protocol_version": 1, "min_protocol": 1,
                     "server_version": "<semver движка>", "pid": 4312}}
```

- `protocol_version` — текущая версия протокола сервера; `min_protocol` —
  нижняя граница dual-поддержки при будущих переходах; `server_version` —
  версия движка (не контракта); `pid` — диагностика (pidfile контрактом не
  предусмотрен: single-instance решает probe, § 4.2).

### 4.5 Методы v1

#### `hello`

| Запрос | Ответ | Ошибки |
|---|---|---|
| `params: {"protocol_version": N}` | `{"protocol_version": 1, "min_protocol": 1, "server_version": "...", "pid": N}` | 4 (+`data.supported`), 3, 1 |

#### `status`

Карта состояний (FSM-состояния из specs/service-lifecycle/v1; на момент v1:
`stopped`, `starting`, `healthy`, `degraded`, `backoff`, `blocked` — источник
истины: таблица переходов service-lifecycle § 3.3) + health-флаги.

| Запрос | Ответ | Ошибки |
|---|---|---|
| без params — всё дерево; `params: {"component": "<name>"}` — один компонент | `{"supervisor": {"pid": N, "health": "..."}, "components": {"<name>": {"state": "<fsm-state>", "health": "healthy\|degraded\|down"}}}`; при `component` ключ `supervisor` опускается | 100 |

Минимальная запись компонента — `state` + `health`; дополнительные поля
(tier, счётчики рестартов) аддитивны; их состав определяет
service-lifecycle.

#### `start` — идемпотентен (MUST)

| Запрос | Ответ | Ошибки |
|---|---|---|
| `params: {"component": "<name>"}` | уже запущен → `{"state": "already-running"}`; иначе `{"state": "<fsm-state>"}` | 100, 101, 102 |

#### `stop` — идемпотентен (MUST)

| Запрос | Ответ | Ошибки |
|---|---|---|
| `params: {"component": "<name>", "force"?: false}` | уже остановлен → `{"state": "already-stopped"}`; иначе `{"state": "<fsm-state>"}` | 100, 101, 103 |

`force: true` → пропуск graceful-фазы (POSIX-сигнал завершения и ожидание
выхода); SIGKILL после короткой задержки. Величина задержки и stop-тайминги
— дом specs/service-lifecycle/v1.

#### `restart`

| Запрос | Ответ | Ошибки |
|---|---|---|
| `params: {"component": "<name>"}` | `{"state": "<fsm-state>"}` | 100, 101, 102, 103 |

Семантика фаз и поведение в граничных состояниях — specs/service-lifecycle/v1;
сокет-контракт фиксирует только envelope. Идемпотентность для `restart` не
заявляется.

#### `logs`

| Запрос | Ответ | Ошибки |
|---|---|---|
| `params: {"component": "<name>", "follow"?: false, "tail"?: 100}` | см. ниже | 100, 3 |

- `follow: false` (дефолт) → один ответ:
  `{"result": {"lines": ["...", "..."]}}` — до `tail` строк, `tail ≤ 10000`.
- `follow: true` → **ПОТОК** фреймов
  `{"id": N, "stream": {"component": "<name>", "line": "..."}}` до
  финального ответа. Штатное завершение источника (остановка компонента) →
  финальный ответ `{"id": N, "result": {"state": "<fsm-state>"}}`;
  внутренняя ошибка → error. Клиент MAY разорвать соединение в любой
  момент; сервер MUST освободить ресурсы подписки. Лимиты и тайминги
  follow-потоков (подписки на пира/установку, idle-таймаут, потолок
  длительности) — § 4.7.

#### `health`

Глобальное / по-компонентное здоровье. Значения: `healthy` \| `degraded` \| `down`.

| Запрос | Ответ | Ошибки |
|---|---|---|
| без params — глобальное + все компоненты; `params: {"component": "<name>"}` — один | без params: `{"health": "...", "components": {"<name>": "..."}}`; с component: `{"health": "..."}` | 100 |

Правила агрегации (тиры core/optional) — specs/service-lifecycle/v1.

### 4.6 Коды ошибок — MUST

| Код | Имя | Значение |
|---|---|---|
| 1 | `bad_request` | malformed-кадр, нарушение формы envelope (запрос до `hello` — код 4, § 4.4) |
| 2 | `unknown_method` | метод не существует (клиенты MAY пробовать новые методы и корректно обрабатывать отказ) |
| 3 | `invalid_params` | неверные типы/значения params (в т.ч. провал regex имени, `tail` вне диапазона) |
| 4 | `version_unsupported` | несовпадение major; любой запрос до `hello` (версия не согласована, `data.reason="hello_required"`); `data.supported` ОБЯЗАТЕЛЕН |
| 100 | `unknown_component` | имя корректно, но отсутствует в реестре манифестов |
| 101 | `invalid_state` | переход запрещён текущим FSM-состоянием |
| 102 | `start_failed` | старт не удался; причина — в `data` |
| 103 | `stop_timeout` | graceful-таймаут истёк без выхода процесса |
| 200 | `permission_denied` | отказ авторизации на сервере (system-профиль: peer-чек не прошёл; будущий ACL) |
| 500 | `internal` | внутренняя ошибка; детали — в логах супервайзера, не клиенту |

Диапазоны: `<100` — протокол; `100–199` — lifecycle; `200` — authz;
`500` — infra. Клиент, получивший неизвестный код, MUST трактовать его по
диапазону. Новый код внутри существующего диапазона — аддитивное изменение
(MINOR, § 8).

**Гигиена `data` ошибок диапазона 100–199 (MUST).** В `data` допускаются
только машинообразуемые поля: имя компонента, FSM-состояние, код выхода.
Пути, env-строки и argv ЗАПРЕЩЕНЫ в error-данных — они могут нести секреты
и внутренние детали установки.

### 4.7 Лимиты и запреты — MUST

| Лимит | Значение | При нарушении |
|---|---|---|
| Длина строки запроса | ≤ 1 MiB | error 1 и/или закрытие соединения |
| Таймаут ответа | 10 s (кроме follow-потоков) | клиент закрывает соединение; повтор идемпотентных операций безопасен |
| Одновременных follow-подписок | не более 2 на пира и не более 8 на установку | сверх — error 3 `invalid_params` |
| Idle-таймаут фрейминга follow | 60 s | нет данных для кадра — сервер закрывает поток финальным ответом |
| Длительность follow-потока | ≤ 3600 s (жёсткий потолок) | авто-закрытие финальным ответом; клиент переподписывается |
| `tail` | ≤ 10000, дефолт 100 | error 3 |
| Имя компонента | `^[a-z][a-z0-9-]{0,62}$` (полный шаблон имени манифеста) и наличие в реестре манифестов | regex-провал → 3; нет в реестре → 100 (защита от name-инъекции в `logs`) |
| Транспорт | только `AF_UNIX` | TCP control plane ЗАПРЕЩЁН по умолчанию; его появление = новая trust boundary → MAJOR + полный threat model |

| CLI | Метод сокета |
|---|---|
| `vesma service status` | `status` |
| `vesma service logs [--follow] [--tail N]` | `logs` |
| `vesma service start <component>` | `start` |
| `vesma service stop <component> [--force]` | `stop` |
| `vesma service restart <component>` | `restart` |

клиенту; отдельная CLI-команда — MAY (аддитивное расширение).

## 5. Threat model (мини-STRIDE)

**Активы.**
A1 — управление жизненным циклом дочерних процессов (start/kill) = полный
контроль над системой пользователя. A2 — поток логов компонентов. A3 —
доступность супервайзера как единственной точки управления.

**Границы доверия.**
B1 — файловая система → сокет (кто дошёл до пути). B2 — peer-соединение →
супервайзер (кто реально подключился). B3 (горизонт v2) — оператор →
system-сокет.

| Угроза | Класс | Митигация | Проверка |
|---|---|---|---|
| Посторонний локальный пользователь подключается к сокету | S (Spoofing) | DAC 0700/0600; `SO_PEERCRED` defense-in-depth: peer uid == владелец сокета, иначе immediate close (system-профиль: uid=root или gid=vesma-oper на каждый accept + audit) | conformance 1, 3 |
| Symlink-подмена пути сокета, подмена каталога | T (Tampering) | `lstat` перед unlink (только свой socket-файл; symlink → отказ + алерт, никогда не follow); `fstat` после bind; pre-flight клиента на lax-каталог (§ 4.1) | conformance 2, 5, 6 |
| Stale-сокет как ложный инстанс, потеря single-instance | E / D | `connect()`-probe перед unlink; pidfile не нужен — probe решает; слепой unlink живого сокета запрещён | conformance 4, 7 |
| Инъекция имени компонента в `logs` (path traversal) | E (Elevation of Privilege) | regex `^[a-z][a-z0-9-]{0,62}$` + валидация против реестра манифестов | conformance 13 |
| TCP-экспозиция control plane | I / S | запрещена by construction (unix-only; включение = MAJOR + полный threat model) | conformance 15 |
| Downgrade протокола | T | `hello`: проверка major `protocol_version`; несовпадение → error 4 + `supported` | conformance 9 |
| Flood соединений / гигантских строк против супервайзера | D (DoS) | лимит строки 1 MiB; таймаут ответа 10 s; CLI не держит постоянных соединений кроме `logs --follow` | conformance 12, 14 |
| «Кто это сделал?» | R (Repudiation) | v1 user-профиль: один владелец = один оператор — риск низкий; супервайзер журналирует методы в свой лог; system-профиль (v2): deny + обязательная audit-строка | операционный контроль; v2 — conformance |

Каждая митигация — либо пункт conformance-чеклиста (номер указан), либо
«операционный контроль». Гигиена содержимого логов (секреты и т.п.) — вне
сокет-контракта: дом компонентов и service-lifecycle; сокет не добавляет
здесь поверхность.

## 8. Совместимость и эволюция

- **SemVer** по правилам репозитория (README, «Дисциплина контрактов»):
  MAJOR — ломающее (формат envelope, семантика методов, пути/права);
  MINOR — аддитивное (новый метод, новый код в существующем диапазоне,
  новое поле ответа); PATCH — редакционное.
- **Механизм переговоров** — `hello` с major-only проверкой (§ 4.4);
  ломающее изменение версии протокола = новый MAJOR + dual-окно через
  `min_protocol`.
- **Неизвестные методы** — error 2; клиент MAY пробовать новые методы и
  деградировать корректно (основа dual-поддержки).
- **Неизвестные коды ошибок** — трактуются по диапазону (§ 4.6).
- **Неизвестные поля** `result`/`stream` клиент MUST игнорировать
  (аддитивная эволюция ответов).
- **Мост на JSON-RPC 2.0** — envelope сознательно совместим по форме;
  будущий мост дёшев (§ 1.3).

## 9. Миграция с легаси

До 2026-10-04 управление компонентами — ad hoc (инвентарь в брифе
директивы `vesma-cli-service-management-directive-20261004`): 5 механизмов
запуска, 2 scope systemd-юнитов, pkill-паттерны в `ExecStop`, дубль-сервисы,
статус «по процессам» (pgrep/pkill). Контракт заменяет:

- правду о состоянии — из сокета, не по процессам;
- остановку — через супервайзер (stop-семантика манифестов), не
  pkill-паттерны;
- один systemd-юнит над процессом супервайзера (дом service-lifecycle);

Правила перехода:

1. Реализация движка (карточка `cli-service-management`) вводит сокет до
   массовой миграции компонентов; статус спеки меняется `draft` →
   `stable` первой конформанной реализацией.
2. Для мигрировавшего (есть манифест в реестре) компонента управление —
   только по контракту; параллельные каналы (TCP/HTTP control plane,
   сокеты вне лэйаута) запрещены § 4.7.
3. Старые механизмы могут запускать ещё не мигрировавшие компоненты в
   период сосуществования; их утилизация — по списку учредительного
   брифа (founding context, `docs/`).
4. Миграция легаси-развёртывания — не ранее закрытия первого окна
   наблюдения учредительного трека (founding context — см. `docs/`;
   рестарты сегментируют наблюдение).

**Историческая справка.** Спека намеренно генерифицирована (решение
владельца 2026-10-04): конкретика учредительного окружения — легаси-имена,
целевая машина, детали первого окна наблюдения — сохранена в founding-паке
`docs/` (в частности, бриф директивы
`docs/brief-2026-10-04-archcom-founding.md`) и в истории репы; для
связности истории читай их вместе с этой спекой.
