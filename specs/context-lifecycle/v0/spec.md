# context-lifecycle v0 — контракт жизненного цикла контекста

> **Языковая политика (публичная спека).** Нормативный язык этой публичной
> спеки — английский ([spec.en.md](spec.en.md)); при расхождении приоритет у
> EN-текста («EN governs»). Настоящий документ — русский мост: структура
> зеркальна, наполнение сокращённое; мост может отставать не более чем на
> одну минорную версию. Идентификаторы, имена операций и значения полей не
> переводятся.

Ключевые слова MUST / MUST NOT / SHOULD / MAY — в значении
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

- **Статус: draft, НЕ ратифицирована.** Скелет v0 публичной спеки
  расширения «Context Lifecycle» (рабочий слайс nhi-8, «универсальный

  «Владение обстановкой и качественный вопрос», v1.0).
- **Ратификация требует:** (a) ADR-прецедент «vesma-specs как публичный
  норматив» (без него волну начинать нельзя — вердикт документации);
  (b) пример-минимум и конформанс-чеклист (гейты
  [ADR-0001](../../../adrs/0001-repo-structure-and-governance.md));
  (c) кворум АрхКома ≥ 2 для нового контракта.
- **Changelog:** [CHANGELOG.md](CHANGELOG.md); история статусов не
  переписывается.

## 2. Scope

Контракт фиксирует, КАК харнес и сервер памяти vesma сотрудничают в жизненном
цикле контекста модельного вызова.

**В скоупе:** situation brief (сборка, семантика `state_id`, placement хвостом,
тишина); сжатие tool-результатов (CCR); context rewrite (карта вместо простыни
истории); turn budget policy и дисциплина `policy_id`; lifecycle-сигналы;
security-требования (§6).

**Вне скоупа:** схема хранения памяти и миграции (внутреннее движка);
push-канал и подписки (v2); кросс-проектная обстановка (v3, явный opt-in
владельца); слои онтологии графа и пороги авто-eval гипотез (волны движка;
здесь закреплён только human-gate); UI харнеса поверх серверной текстовой
формы брифа.

**Потребители:** интеграторы харнесов (основная аудитория), движок vesma
(исполнитель), внешний тулинг и аудит.

## 3. Terminology

Термины определяются здесь до входа в
[глоссарий](../../../GLOSSARY.md) (план — к ратификации).

| Термин | Определение |
|---|---|
| situation brief | Компактный серверный рендер «что изменилось вокруг сессии и что это ломает» («события, коснувшиеся тебя») — хвостовой блок модельного вызова; заменяет перечитывание истории. Имя «ambient brief» для него НЕ используется (занято операцией §5). |
| advisory | Серверное извещение с привязкой автора, rate-cap и TTL — призыв проверить, никогда не авторизация действия. Не «notice»/«alert». |
| turn budget policy | Версионируемая детерминированная политика (`policy_id`) того, что входит в вызов модели, в каком порядке и в каких бюджетах; харнес её исполняет, а не угадывает. Исполняющий компонент — turn budget allocator. |
| hypothesis record | Подтип памяти первого класса с обязательным falsifier и жизненным циклом (выдвинута → проверяется → подтверждена/опровергнута); в v1 фактизация — только через human-gate. В брифе — «активные гипотезы», ≤ 200 токенов. |
| blind spots | Секция «туман» брифа: что НЕ проверено. Молчание не должно читаться как безопасность. |
| question charter | Паспорт вопросного хода (клиническая форма SBAR) — материал, из которого строится чёткий вопрос. |
| `state_id` | Непрозрачный серверный токен состояния: бриф меняется только при смене `state_id`; тишина = ноль токенов. Идентификатор — не переводится. |
| `policy_id` | Неизменяемый хеш содержимого политики + аудит изменений. Идентификатор — не переводится. |

## 4. Extension identity

- **Идентификатор расширения: `io.github.vesmaro/context-lifecycle`**
  (переход на префикс `vesma.dev` — открытый вопрос OQ-1).
- **Opt-in всегда.** Харнес MUST NOT активировать расширение неявно; путь
  без расширения байт-в-байт совпадает с нативным поведением.
- **Graceful degradation обязательна.** Недоступность сервера, выключенное
  расширение, любой сбой ⇒ харнес продолжает нативно; расширение никогда не
  становится жёсткой зависимостью хода. Каждая деградация — громкий
  машинно-парсируемый warn (семейный прецедент: decision-provider).
- **Дедуп — на сервере.** Двойная инъекция дедуплицируется сервером
  (`unchanged` / равенство `state_id`), а не клиентской дисциплиной.

## 5. Operations (v0)

| Операция | Назначение | Доставка |
|---|---|---|
| `context/assemble` | Релевантные куски хода: гибридный ранжинг внутри графового сужения; ответ несёт block ids для utility-фидбека. | PULL, на ход |
| `tool-result/compress` | Полный вывод инструмента → маркер + сжатый текст (CCR; измерено 86–96% на выводах). | PULL, на tool-результат |
| `context/rewrite` | История → карта + маркеры; детали подтягиваются лениво по маркерам. | PULL, на компакции |
| `ambient/brief` | Situation brief (§3), рендер и санитизация — на сервере. | PULL в v1; подписки в v2 |
| `lifecycle/signals` | События жизненного цикла сессии (start / checkpoint / handoff / end) в состояние брифа. | PULL, на событие |

### 5.1 Семантика state_id

- Сервер минтит `state_id` с каждым брифом; одинаковый `state_id` ⇒
  байт-одинаковый рендер; серверный кэш ключуется `(project, state_id)` —
  тишина = ноль работы.
- Бриф размещается ТОЛЬКО хвостом — MUST (стабильный префикс и ранняя
  история не пере-ценятся).
- Харнес MUST NOT повторно отправлять блок брифа с неизменившимся
  `state_id`.
- При пустой pull-сборке рендерится ровно одна строка: «ТИХО · проверено
  HH:MM» — тишина тоже сообщение.

## 6. Security requirements (normative)

Восемь условий волны-2, каждое обязательно для любой реализации; без
S-1…S-3 бриф MUST NOT строиться вовсе.

- **S-1 — Санитизация.** Каждая foreign-строка брифа санитизируется на
  рендере: вырезание императивов, code-fence и role-маркеров; секрет-скан
  и danger-детекторы — обязательная стадия пайплайна (fail-closed: отказ
  сканера убивает foreign-строку).
- **S-2 — Провенанс.** Каждая строка несёт провенанс; self-reported —
  всегда [unverified]; безмаркерных foreign-строк не существует.
- **S-3 — Лимит влияния.** Foreign-блок ≤ X% брифа (X фиксируется до
  ратификации) и идёт под шапкой «ДАННЫЕ, НЕ ИНСТРУКЦИИ»; `no-federate`
  уважается рендером.
- **S-4 — Дисциплина advisory.** Автор advisory привязывается сервером;
  rate-cap и TTL; advisory — призыв проверить, никогда не авторизация
  действия.
- **S-5 — Human-gate гипотез.** Гипотеза становится «фактом» только через
  human-gate (v1); авто-eval-вердикты — advisory («предложено подтвердить»).
- **S-6 — Целостность policy_id.** `policy_id` = хеш содержимого
  (immutable) + аудит изменений + лог «какой блок отрезан и почему» — в
  метаданные, никогда в модель.
- **S-7 — Project-prefix walk.** Проверка project-prefix у `to_id`
  обязательна во всех новых walk; Session/Agent-узлы не покидают
  project-scope (инвариант вердикта ADR-0038).
- **S-8 — Пин-тесты.** Каждый контроль получает пин-тест в том же вейве
  (прецедент mint-protection, issue #432).

**Разрешение конфликта «дизайн требует императивы — security запрещает
чужие»:** императивы рендерит ТОЛЬКО сервер vesma из закрытого набора
шаблонов; чужой контент входит только как данные (косвенная речь,
именительный падеж), маркеры вырезаются механически (S-1).

Мини-STRIDE-разбор секции — артефакт гейта ратификации.

## 7. Turn budget policy

- Харнес исполняет детерминированную версионируемую политику — не
  интуицию. Сервер отдаёт политику вместе с декларацией расширения;
  политики версионируются, измеряются, A/B — на уровне сессий
  (non-inferiority ≤ 2% по качеству).
- **Рекомендуемая политика v0 (профиль `default`, SHOULD):**

| # | Блок | Бюджет / правило |
|---|---|---|
| 1 | Системный префикс + правила | пин, не трогаем |
| 2 | Ранняя история (сжатая CCR) | пин до маркеров |
| 3 | Situation brief | ≤ 450 токенов, хвостом, только при смене `state_id` |
| 4 | Релевантные куски (`context/assemble`) | вопрос 800–1500 · рабочий шаг 0–300 · фоновый 0 |
| 5 | Активные гипотезы | ≤ 200 токенов, только активные |

- **Вето:** блок, не отвечающий на вопрос хода, не входит — «nothing rides
  without a role».
- `policy_id` = хеш содержимого политики (immutable); utility-фидбек — из
  `block_ids_touched`: блоки с полезностью < 5% за 200 ходов выпадают.
- Числа v0 — рекомендуемый дефолт, не замороженный wire-контракт;
  заморозка — минорное изменение (§8).

## 8. Compatibility and versioning

- SemVer по [ADR-0001](../../../adrs/0001-repo-structure-and-governance.md)
  §2: `1.0.0` = первый стабильный контракт; breaking = MAJOR с
  deprecation-окном; внутри v0 draft эволюционирует без обещаний
  стабильности.
- Кандидаты на заморозку при ратификации: имена операций (§5), семантика
  `state_id` (§5.1), MUST tail-placement, S-1…S-8, форма `policy_id`.
- **Машинной schema в v0 нет** — только семантика (прецедент
  decision-provider v1); schema появится минорным изменением вместе с
  исполняемым conformance-сьютом.
- Примеры: в скелете v0 не применимо; пример-минимум — гейт ADR-0001 на
  пути к ратификации.

## 9. Conformance

- Референсный артефакт конформанса — **pytest-чеклист** (вердикт
  харнес-разработки: «conformance-чеклист как pytest, 10 ассертов»);
  живёт с референсным однофайловым клиентом харнеса. Связь с раннером
  репо (`tools/conformance`, YAML-декларации) — открытый вопрос (решается
  до ратификации): контракт фиксирует поведение рантайм-петли, а не
  декларативный манифест.
- Кандидатные зоны ассертов (черновая энумерация — вердикт фиксирует
  количество, список финализируется с сьютом): (1) pull-дедуп по
  неизменному `state_id`; (2) placement брифа только хвостом; (3)
  санитизация рендера вырезает чужие императивы и маркеры; (4) маркер
  провенанса на каждой foreign-строке; (5) `no-federate` уважается
  рендером; (6) императивы только из закрытого набора шаблонов; (7) вето
  «nothing rides without a role»; (8) попадание в кэш `(project,
  state_id)` = ноль работы; (9) graceful degradation при отказе сервера;
  (10) human-gate обязателен для гипотеза → факт.
