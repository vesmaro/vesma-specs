# layout v1 — канонический лэйаут

> **Статус: stable (1.0.0).** Ратифицирован первой конформной реализацией
> в движке `vesma` 2026-10-05 (main `4a2da5a`; конформанс —
> docs/project/reports/service-conformance-2026-10-06.md в репо движка,
> раннер 24/24, чеклист LY-01…LY-14 green). Форма контракта — профили
> установки и пути, права, единственность мест логов, venv-дисциплина,
> doctor-проверки, миграция с легаси — ратифицирована учредительным
> АрхКомом VESMA 2026-10-04 (ADR-0001) и здесь **кодифицируется, а не
> переигрывается**. Дальнейшие изменения — только через SemVer-процесс (§7).

Ключевые слова MUST / MUST NOT / SHOULD / MAY интерпретируются по RFC 2119.
Проза — русская; идентификаторы и пути — канонические (EN).

## 1. Scope

Лэйаут — deb-подобная дисциплина каталогов инсталляции VESMA (глоссарий:
Canonical layout): где конфиги, манифесты, секреты, данные, venv, логи,
runtime и кэш. Контракт закрывает инвентарный хаос легаси — логи в трёх
местах, конфиги в легаси-именах, venv-перекрытия (инвентарь — бриф
директивы `vesma-cli-service-management`, см. [ADR-0001](../../../adrs/0001-repo-structure-and-governance.md)).

**В скоупе:**

- профили установки user/system и правило соответствия 1:1;
- канонические пути и права user-профиля (таблица MUST §3.2);
- канонизации, снимающие плейсхолдеры соседних контрактов: каталог
  манифестов = `~/.config/vesma/components.d/<name>.yaml` (drop-in);
  имя сокета = `control.sock`; каноническое место env-файлов;
  каноническое место конфиг-схем компонентов
  `~/.local/share/vesma/<name>/config.schema.json` — резолв
  `config.schema_file` манифеста от data-каталога компонента (§3.2);
- расширение плейсхолдеров argv (`{config_path}`, `{data_dir}`,
  `{runtime_dir}`, `{venv_bin}`) в конкретные пути (§3.4);
- единственность мест логов: journald / files-under-state, других мест нет;
- venv-дисциплина: один venv на python-юнит, `PYTHONNOUSERSITE=1`,
  пин-политика зависимостей;
- правило кэша: регенерируемое, никогда не секреты (enforcement на уровне
  API записи);
- doctor-проверки инсталляции (`vesma doctor --service`, DR-01…DR-13);
- миграция с легаси: целевые пути (§9) — исполнение миграции не здесь.

**Вне скоупа (домены соседних контрактов):**

- форма манифеста и правила `env_file` —
  [specs/component-manifest/v1](../../component-manifest/v1/spec.md):
  лэйаут фиксирует **где**, манифест — **что** и как валидируется;
- поведение супервайзера, FSM, юнит-шаблон, hardening —
  [specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md):
  лэйаут даёт `ReadWritePaths`-пути, SL — что с ними делает юнит;
- протокол сокета, TOCTOU-процедура, peer-аутентификация —
  [specs/control-socket/v1](../../control-socket/v1/spec.md):
  лэйаут фиксирует место и права сокет-каталогов;
- содержимое конфигов и секретов в них — config-схема манифеста
  (CM §3.9) и env-файлы (CM §3.5);
- реализация миграции легаси-развёртывания — движок (карточка
  `cli-service-management`), не ранее закрытия первого окна наблюдения
  учредительного трека (founding context);
- hash-pinning-тулинг (механика `pip --require-hashes`, lock-тулинг) — v2.

**Потребители:** движок `vesma` (install-флоу — единственный писатель
установки; супервайзер — читатель-исполнитель; `doctor` — проверяющий),
компоненты (потребляют пути через плейсхолдеры, не хардкодят их),
conformance-раннер `tools/conformance`, внешние интеграторы.

## 2. Терминология

Термины Canonical layout, Runtime directory, venv discipline, Supervisor,
Component, Manifest определены в [глоссарии](../../../GLOSSARY.md) и здесь
не переопределяются. Контрактные термины:

| Термин | Значение |
|---|---|
| профиль установки | user (v1, реализуемый) или system (определён §3.3, реализация отложена за v2); system строится таблицей соответствия user-путям 1:1 |
| канонический путь | путь из таблиц §3.2/§3.3; хардкод иных мест в инсталляционных артефактах — нарушение контракта |
| drop-in каталог | каталог, единицей содержимого которого является один файл `<name>.yaml`; install кладёт файл, uninstall убирает; операции не трогают чужие файлы |
| files-under-state | файловый режим логов в `~/.local/state/vesma/logs/<name>/` — только когда journald недоступен (контейнер / ручной режим) |
| fallback runtime | `~/.local/state/vesma/run/` — runtime-каталог при пустом `XDG_RUNTIME_DIR` + WARN-строка (спека control-socket v1 §3) |
| fail-closed загрузчик | определён в [specs/component-manifest/v1](../../component-manifest/v1/spec.md) §2: любое нарушение условий загрузки `env_file` = отказ старта, не предупреждение |
| freeze-дрейф | расхождение фактического содержимого venv (`pip freeze`) с lock-файлом установки |
| user-site | per-user каталог site-packages интерпретатора (PEP 370); утечка = попадание user-site в `sys.path` процесса |
| history | append-only журнал переходов супервайзера: `~/.local/state/vesma/history/` |
| doctor | диагностическая команда `vesma doctor --service`; чеклист DR-01…DR-13 (§3.10) |
| first observation window | первое окно телеметрии учредительного трека (founding context); миграция легаси-развёртывания не исполняется до его закрытия (roadmap фаза 3; детали — founding-пак `docs/`) |

## 3. Контракт

### 3.1 Профили и базовые каталоги

- **MUST**: user-профиль — единственный реализуемый в v1.
- **MUST**: пути user-профиля строятся по XDG Base Directory Specification:
  `$XDG_CONFIG_HOME` (дефолт `~/.config`), `$XDG_DATA_HOME` (дефолт
  `~/.local/share`), `$XDG_STATE_HOME` (дефолт `~/.local/state`),
  `$XDG_CACHE_HOME` (дефолт `~/.cache`); пустая переменная = дефолт.
  В таблицах ниже пути записаны по дефолтам.
- **MUST**: владелец всех путей user-профиля — пользователь супервайзера.
- **MUST**: права каталогов и файлов выставляются явно при создании
  (`chmod` после `mkdir` / перед использованием), а не наследуются от
  umask (симметрично примечанию B к §3 спеки control-socket v1).
- **MUST**: каталог, права которого ослаблены относительно таблицы §3.2,
  fail-closed для соответствующей операции (§3.5): операция не выполняется
  «с предупреждением».

### 3.2 User-профиль (v1, нормативный)

Таблица MUST:

| Путь | Содержимое | Права |
|---|---|---|
| `~/.config/vesma/vesma.yaml` | общий конфиг; конфиг компонента = секция общего конфига (CM §3.9) | каталог `0700` |
| `~/.config/vesma/components.d/<name>.yaml` | манифесты компонентов (drop-in; install кладёт, uninstall убирает) | каталог `0700` |
| `~/.config/vesma/env/<name>.env` | env-файлы секретов | файл `0600`; fail-closed загрузка (не `0600` / чужой владелец = отказ старта + готовая команда исправления) |
| `~/.local/share/vesma/<name>/` | данные компонента; default cwd ребёнка | каталог `0700` |
| `~/.local/share/vesma/<name>/config.schema.json` | конфиг-схема компонента; кладёт install-флоу вместе с данными компонента; резолв `config.schema_file` манифеста (CM §3.9) — от data-каталога компонента | каталог `0700` (data-каталог компонента) |
| `~/.local/share/vesma/venv/` | venv движка (supervisor runtime): движок + in-process модули (§3.8); единственный venv вне `venvs/`; имена компонентов `venv`/`venvs` зарезервированы (валидатор имён отклоняет) | каталог `0700` |
| `~/.local/share/vesma/venvs/<name>/` | venv python-компонента-ребёнка | каталог `0700` |
| `~/.local/state/vesma/logs/<name>/` | файловые логи (когда journald нет); ротация 10 MB × 5 | каталог `0700` |
| `~/.local/state/vesma/history/` | журнал переходов супервайзера (append-only) | каталог `0700` |
| `~/.local/state/vesma/run/` | fallback runtime (сокет, pids) при пустом `XDG_RUNTIME_DIR` + WARN | каталог `0700` |
| `${XDG_RUNTIME_DIR}/vesma/` | канонический runtime: `control.sock` `0600`, pids | каталог `0700` |
| `~/.cache/vesma/<name>/` | регенерируемое; НИКОГДА не секреты (правило на уровне API записи, §3.9) | каталог `0750` |

Примечания:

- **a.** Default cwd ребёнка — data-каталог компонента (`{data_dir}`,
  §3.4); манифест задаёт `cwd` явно (CM §3.5), install-флоу проставляет
  каноническое значение по умолчанию.
- **b.** `venvs/<name>/` создаётся **только** для python-компонентов-детей;
  in-process компоненты живут на venv движка (§3.8) и собственного venv не
  имеют, не-python дети venv не имеют.
- **c.** Файловые логи — только в режиме files-under-state (§3.7); при
  systemd каталог `logs/` может не создаваться вовсе.
- **d.** Кэш **MAY** не существовать — создаётся лениво при первой записи;
  удаление каталога кэша безопасно в любой момент.
- **e.** pids — диагностические pid-файлы; single-instance обеспечивается
  connect-probe (control-socket v1 §4.2), не pid-файлом.
- **f.** Файлы общего конфига (`vesma.yaml`) **SHOULD** быть не
  группо-/миро-читаемыми (`0600`): секреты в `vesma.yaml` запрещены (дом
  env-файлов), но конфиг не обязан быть публичным.

### 3.3 System-профиль (определён, реализация отложена)

**Реализация system-профиля отложена за миграцию легаси-развёртывания —
не ранее закрытия первого окна наблюдения учредительного трека (founding
context); горизонт v2** ([ADR-0001](../../../adrs/0001-repo-structure-and-governance.md),
горизонт v2). Таблица соответствия XDG 1:1 нормативна как дизайн-референс;
конформанс-пункты system-профиля — `n/a (v2)`.

| Назначение (user, §3.2) | System-путь | Права |
|---|---|---|
| общий конфиг | `/etc/vesma/vesma.yaml` | `0640 root:vesma` |
| манифесты компонентов | `/etc/vesma/components.d/<name>.yaml` | `0640 root:vesma` |
| env-файлы секретов | `/etc/vesma/env/<name>.env` | `0600 root:vesma` |
| данные компонента / default cwd | `/var/lib/vesma/<name>/` | фиксируется при реализации (v2) |
| venv python-компонентов | `/var/lib/vesma/venvs/<name>/` | фиксируется при реализации (v2) |
| runtime (сокет, pids) | `/run/vesma/` | `0750 root:vesma-oper`; `control.sock` `0660` — см. [specs/control-socket/v1](../../control-socket/v1/spec.md) §3 |
| файловые логи | `/var/log/vesma` в v1 **НЕ создаётся** | — |

- **MUST NOT**: `/var/log/vesma` не создаётся ни в user-, ни в
  system-профиле v1.
- **MUST**: env-файлы секретов — `0600 root:vesma`, единое правило с
  user-профилем (§3.2): групповое чтение секретов противоречит fail-closed
  загрузчику (CM §3.5, `ENV_FILE_UNSAFE`); общий конфиг и манифесты — не
  секреты, остаются `0640 root:vesma`.
- Остальные строки system-соответствия (history, кэш) строятся при
  реализации v2 по тому же принципу 1:1 и **MUST NOT** противоречить этой
  таблице.
- Группа `vesma-oper` инсталлятором по умолчанию **НЕ создаётся**
  (control-socket v1 §3, примечание D): её создание — осознанное действие
  оператора на горизонте v2.

### 3.4 Расширение плейсхолдеров argv

Плейсхолдеры манифеста (allowlist — CM §2) расширяет супервайзер при spawn
по таблице MUST:

| Плейсхолдер | User-профиль | System-профиль |
|---|---|---|
| `{config_path}` | `~/.config/vesma/vesma.yaml` | `/etc/vesma/vesma.yaml` |
| `{data_dir}` | `~/.local/share/vesma/<name>/` | `/var/lib/vesma/<name>/` |
| `{runtime_dir}` | `${XDG_RUNTIME_DIR}/vesma/` (fallback: `~/.local/state/vesma/run/`) | `/run/vesma/` |
| `{venv_bin}` | `~/.local/share/vesma/venvs/<name>/bin` | `/var/lib/vesma/venvs/<name>/bin` |

- **MUST**: других подстановок нет — никакой интерполяции переменных
  окружения и никакого shell (CM §3.5); расширение выполняет супервайзер.
- **MUST**: `{venv_bin}` у компонента без venv не расширяется; отсутствие
  venv при ссылке на `{venv_bin}` = отказ старта (fail-closed) с
  диагностикой.

### 3.5 Каталог манифестов и env-файлы

- **MUST**: каталог манифестов = `~/.config/vesma/components.d/`; манифест
  компонента `<name>` — файл `components.d/<name>.yaml`. Канонизация
  снимает плейсхолдер `~/.config/vesma/manifests/` из CM §2.
- **MUST**: имя файла манифеста == `metadata.name`; каждый файл в
  `components.d/` обязан быть валидным манифестом — невалидный файл =
  ошибка загрузки установки (fail-closed), не тихий пропуск.
- **MUST**: drop-in дисциплина: install атомарно создаёт/обновляет файл
  манифеста (tmp + rename), uninstall удаляет файл; единственный писатель —
  install-флоу (CM §3.1); компоненты и супервайзер каталог на запись не
  получают (`ReadWritePaths` юнита — SL §3.6).
- **MUST**: env-файлы секретов — `~/.config/vesma/env/<name>.env`, файл
  `0600`, владелец — пользователь супервайзера; `<name>` ==
  `metadata.name` компонента.
- **MUST**: env-файл лежит **вне каталога манифестов** и загружается
  fail-closed: не `0600` / чужой владелец / объявлен, но отсутствует =
  отказ старта с готовой командой исправления (CM §3.5, код
  `ENV_FILE_UNSAFE`).
- **MUST**: install-флоу размещает создаваемые env-файлы только в
  `env/<name>.env`.
- **SHOULD**: `doctor` подсвечивает `env_file` манифеста вне канонического
  места как дрейф (WARN + команда переноса через install).
- **MUST**: каталоги `~/.config/vesma/`, `components.d/`, `env/` — `0700`.

### 3.6 Runtime-каталог и сокет

- **MUST**: канонический runtime = `${XDG_RUNTIME_DIR}/vesma/`, каталог
  `0700`; сокет — `control.sock`, `0600` (канонизация имени согласована со
  [specs/control-socket/v1](../../control-socket/v1/spec.md) §3).
- **MUST**: `XDG_RUNTIME_DIR` пуст → fallback `~/.local/state/vesma/run/`
  (`0700`) + WARN-строка в лог (control-socket v1 §3).
- **MUST**: сокет-артефакты подчинены control-socket v1 целиком:
  TOCTOU/SYMLINK-процедура bind-стороны (§4.2), peer-аутентификация,
  запрет TCP; лэйаут фиксирует только место и права.
- **MUST**: pids — pid-файлы диагностики внутри runtime-каталога;
  **MUST NOT** использоваться как механизм single-instance или блокировки
  (control-socket v1 §4.2: probe решает).
- **MUST NOT**: постоянное состояние в runtime не размещается — runtime
  живёт в tmpfs-семантике `XDG_RUNTIME_DIR`; для постоянного есть
  state/data/history.

### 3.7 Логи и журнал переходов

- **MUST** (канон при systemd): всё в journald; маркировку
  `SYSLOG_IDENTIFIER=vesma-<component>` выполняет супервайзер при пересылке
  строк детей (SL §3.4); `vesma service logs` = journalctl-фильтр по
  идентификатору (control-socket v1 §4.5/4.8), не grep по файлам.
- **MUST** (контейнер / ручной режим, journald недоступен):
  files-under-state — `~/.local/state/vesma/logs/<name>/`; ротация
  10 MB × 5 файлов; формат строк — структурные строки SL §3.4.
- **MUST**: режим выбирается ровно один: journald доступен → journald
  (файловые логи не пишутся); недоступен → files-under-state. Двойная
  запись в оба места запрещена.
- **MUST NOT**: никаких иных мест логов — ни разрозненных легаси файловых
  логов, ни логов в data-каталоге, ни в кэше, ни `/var/log/vesma` (§3.3).
  Появление «третьего места» = нарушение контракта (закрывает инвентарный
  хаос «логи в 3 местах»: journald + разрозненные файловые логи + разное).
- **MUST**: `~/.local/state/vesma/history/` — append-only журнал переходов
  супервайзера (`0700`); содержимое — структурные строки (дом SL §3.4);
  лэйаут фиксирует путь, права и append-only семантику.

### 3.8 venv-дисциплина

- **MUST**: один управляемый venv на один python-юнит рантайма. Два класса:
  (а) venv движка — движок + все in-process модули; (б) venv
  python-компонента-ребёнка — `venvs/<name>/` из манифеста.
- **MUST**: ДВА компонента на одном venv = ошибка (install-валидация /
  doctor DR-04). venv не шарится между компонентами и между компонентом и
  движком.
- **MUST**: `venvs/<name>/` (`0700`) — только для python-компонентов-детей.
  venv движка (supervisor runtime) — `~/.local/share/vesma/venv/` (`0700`,
  таблица §3.2): единственный venv вне `venvs/`; резервирует имя — имена
  компонентов `venv` и `venvs` ЗАРЕЗЕРВИРОВАНЫ (валидатор имён манифеста
  их отклоняет). venv движка **MUST NOT** пересекаться ни с одним
  `venvs/<name>/` (DR-06).
- **MUST**: `PYTHONNOUSERSITE=1` инжектируется супервайзером **безусловно**
  в каждый python-процесс (движок и дети) — утечка user-site в `sys.path`
  исключается по построению; `doctor` подтверждает тестом импорта в чистом
  окружении (DR-03).
- **MUST**: зависимости пинуются точно (`==`) против lock-файла
  инсталляции — v1.
- **SHOULD**: hash-pinning (`pip --require-hashes`) — дефолт v1; мандат —
  v2 (нужен lock-тулинг).
- **MUST**: источники пакетов — только PyPI; URL/wheels со стороны
  (прямые ссылки, сторонние индексы) в v1 запрещены.
- **MUST**: site-packages venv не миро- и не группо-записываемы; владелец
  venv — пользователь супервайзера (supply chain граница, §8).
- **SHOULD**: venv наполняется только регенерацией install-флоу; ручной
  `pip install` внутрь `venvs/<name>/` = freeze-дрейф → находка doctor
  DR-02.

### 3.9 Кэш

- **MUST**: `~/.cache/vesma/<name>/` (`0750`) — только регенерируемое
  содержимое; удаление каталога в любой момент не меняет корректность
  инсталляции (содержимое восстанавливается).
- **MUST**: кэш **НИКОГДА** не содержит секреты. Enforcement — на уровне
  API записи движка: значения, происходящие из env-файлов, несут тип
  «секретное» при загрузке (taint); API записи кэша **MUST** отвергать
  значения секретного типа (LY-12). Записи мимо API (same-uid напрямую в
  ФС) — вне контрактного радиуса; ловятся doctor-сверкой
  (`vesma doctor --service`, §3.10).
- **MUST NOT**: конфиги, манифесты, env-содержимое, логи и state-данные в
  кэше не размещаются (их дом — таблица §3.2).

### 3.10 Doctor-проверки (`vesma doctor --service`)

MUST-список проверок инсталляции (исполнение — движок; идентификаторы
DR-xx референсится threat model §8 и чеклистом):

| ID | Проверка | Подробности |
|---|---|---|
| DR-01 | права/владение config/state/env | каталоги `0700`, env-файлы `0600`, владелец — пользователь; отклонение → WARN/FAIL + команда |
| DR-02 | venv integrity | site-packages не миро- и не группо-записываемы; владелец совпадает; `pip freeze` против lock (дрейф = FAIL) |
| DR-03 | утечка user-site | тест импорта в чистом окружении (эквивалент `PYTHONNOUSERSITE`); user-site в `sys.path` = FAIL |
| DR-04 | два манифеста на один venv | уникальность venv на python-юнит; коллизия = FAIL |
| DR-05 | версия python venv vs манифест | ограничение `python.version` манифеста (CM §3.6) против интерпретатора venv; несовпадение = FAIL |
| DR-06 | venv ≠ интерпретатор движка; зарезервированные имена | `venvs/<name>/` не является (и не симлинкует) venv/интерпретатор движка; имя компонента не входит в зарезервированные {venv, venvs} |
| DR-07 | дрейф «сгенерированный юнит vs установленный» | установленный юнит (SL §3.6) == регенерированному; расхождение = FAIL + команда `vesma service install` |
| DR-08 | живость сокета | connect-probe + `hello` по control-socket v1 §4.2; живой супервайзер → OK; stale/отсутствует → статус, не ошибка сам по себе |
| DR-09 | коллизии http/tcp health-портов | пересечение портов health-проб (`health.http`/`health.tcp`, CM §3.7) между манифестами установки = FAIL |
| DR-10 | свободное место | тома канонических корней (config/data/state/cache/runtime); пороги WARN/FAIL — реализация движка |
| DR-11 | `Storage=persistent` у journald | только systemd-контексты; volatile-журнал = WARN (логи теряются при перезагрузке); вне systemd — n/a |
| DR-12 | venv/venvs недоступны на запись в рантайме | `ReadOnlyPaths=` в сгенерированном юните (SL §3.6) покрывает `~/.local/share/vesma/venv` и `~/.local/share/vesma/venvs`; venv'ы создаёт только install-флоу — запись в рантайме = FAIL |
| DR-13 | контейнерный даунгрейд hardening | даунгрейду подверглись только filesystem-директивы (`ProtectSystem`, `ProtectHome`, `ReadOnlyPaths`, `ReadWritePaths`, `PrivateTmp`); даунгрейд иной директивы hardening-блока = FAIL |

- **MUST**: каждая находка несёт severity `OK`/`WARN`/`FAIL` и готовую
  команду исправления с реальным путём («правило комитета»: doctor выдаёт
  готовую команду исправления, а не ругань).
- **MUST**: doctor **НЕ** исполняет команды исправления сам (симметрично
  control-socket v1 §4.1).
- **MUST**: FAIL-находка DR-01 на env-файле согласована с fail-closed
  загрузчиком: старт соответствующего компонента отказан до исправления.

## 8. Threat model (мини-STRIDE)

**Ассеты:** env-файлы с секретами; venv как supply chain (код, исполняемый
супервайзером и детьми); данные компонентов; history (журнал переходов);
кэш — поверхность утечки при нарушении правила.

**Граница контракта:** файловая система лэйаута ↔ супервайзер / загрузчик /
install-флоу / doctor (инсталляция и права).

Остальные границы — домены соседних контрактов, здесь «trust boundaries:
нет»: сокет (peer-аутентификация, TOCTOU) —
[specs/control-socket/v1](../../control-socket/v1/spec.md) §5; env-передача
детям и сигнальное пространство —
[specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md) §7;
загрузка манифеста —
[specs/component-manifest/v1](../../component-manifest/v1/spec.md) §8.

| Категория | Угроза | Митигация | Проверка |
|---|---|---|---|
| **I**nformation Disclosure | lax-права на env/конфиг (umask, ручной `chmod`) — секрет читает другой локальный процесс | fail-closed загрузчик (отказ старта при не-`0600` / чужом владельце) + каталоги `0700` + doctor DR-01 | LY-01, LY-03 |
| **I**nformation Disclosure | секреты в кэше | правило API записи: значение из env-файла не записывается; кэш `0750` | LY-12 |
| **I**nformation Disclosure | логи с секретами расползаются по неучтённым местам | единственность мест логов (journald / files-under-state); двойная запись и «третьи места» запрещены | LY-09; содержимое строк — операционный контроль (redaction — v2, SL §6) |
| **T**ampering | tamper venv/site-packages (supply chain: подмена зависимостей ребёнка/движка) | права `0700`, не миро-/группо-записываемые site-packages; владелец; freeze-дрейф против lock; exact-pin `==` | LY-05, LY-06, LY-08, DR-02 |
| **T**ampering | подмена env-файла (симлинк, чужой владелец, перенос в каталог манифестов) | fail-closed загрузчик `ENV_FILE_UNSAFE`: вне `components.d`, `0600`, свой владелец | LY-02, LY-03 |
| **T**ampering | ручная правка юнита/манифеста мимо install-флоу | единственный писатель — install-флоу (CM §3.1); дрейф-детекция doctor | DR-07, LY-02 |
| **E**levation of Privilege | user-site утечка/перекрытие venv (чужой код в `sys.path` процесса) | `PYTHONNOUSERSITE=1` безусловно в каждый python-процесс + doctor DR-03 | LY-07 |
| **E**levation of Privilege | два компонента на одном venv — взаимное перекрытие зависимостей / подмена модуля | один venv на python-юнит; коллизия = ошибка | LY-05, DR-04 |
| **D**enial of Service | переполнение диска логами / history / кэшем | ротация 10 MB × 5; кэш регенерируем; doctor DR-10 | LY-09, DR-10 |
| **R**epudiation | «кто изменил установку?» | единственный писатель — install-флоу (CM §3.1); history append-only; journald append-only | операционный контроль |
| **S**poofing | подмена супервайзера/CLI на пути сокета | «trust boundaries: нет» в этом контракте — граница домена control-socket v1 §5 (DAC + `SO_PEERCRED` + TOCTOU-процедура) | чеклист control-socket v1 |

Каждая митигация закрыта conformance-чеком (LY/DR) либо помечена
«операционный контроль» — тихих непроверяемых обещаний нет.

## 9. Миграция с легаси

Главная секция этого контракта: лэйаут существует, чтобы у легаси-хаоса
появился целевой путь. Таблица «легаси-путь → канонический путь»
(инвентарь — бриф директивы `vesma-cli-service-management`, 2026-10-04):

| Легаси-путь | Канонический путь (layout v1) | Примечание |
|---|---|---|
| легаси-конфиги с прежними именами в `~/.config` | `~/.config/vesma/vesma.yaml` (общий конфиг) + `~/.config/vesma/components.d/<name>.yaml` (по компоненту) | легаси-имя не сохраняется: содержимое разбирается по назначению — конфиги компонентов против общих настроек |
| разрозненные легаси файловые логи («логи в 3 местах») | journald (systemd) / `~/.local/state/vesma/logs/<name>/` (не-systemd) | одно место по режиму (§3.7); старые файлы архивируются оператором и не продолжаются |
| легаси env-файл с токеном (`0600`) вне канонических путей | `~/.config/vesma/env/<name>.env` (`0600`, fail-closed загрузка) | **SHOULD**: токен при переносе ротируется (ADR-0001 §6: rotate first) |
| данные прежнего развёртывания с тестовыми именами | `~/.local/share/vesma/<name>/` | переименование тестовых имён — отдельная волна движка, не часть этого контракта |
| легаси venv-каталоги с версиями в имени | `~/.local/share/vesma/venvs/<name>/` | один venv на python-юнит; версии в имени venv исчезают; пересоздание из lock, не перенос каталога |
| артефакты отставленного оркестратора | утилизируются (не мигрируют) | — |
| ad-hoc лаунчеры (nohup-скрипты, sh-обёртки) | утилизируются (не мигрируют) | запуск = супервайзер по манифестам (SL) |

**Порядок миграции:** 1) инвентарь `doctor` (DR-01…DR-13 + список
легаси-путей) → 2) перенос по таблице (install-флоу создаёт манифесты /
env / venvs; данные переносятся с владельцем и правами) → 3) зелёный
конформанс компонента → 4) утилизация легаси-механизмов (disable + stop
старых юнитов — SL §8).

- **Миграция легаси-развёртывания — не ранее закрытия первого окна
  наблюдения** учредительного трека (founding context — см. `docs/`);
  исполнение — движок (карточка `cli-service-management`); спека фиксирует
  целевые пути, не исполняет миграцию. Спеки и код CLI окну не подчиняются
  (как в SL §8).
- Точка миграции одна: install-флоу; ручной перенос директив и скриптов
  не предусмотрен.

**Историческая справка.** Спека намеренно генерифицирована (решение
владельца 2026-10-04): конкретика учредительного окружения — легаси-имена,
целевая машина, детали первого окна наблюдения — сохранена в founding-паке
`docs/` (в частности, бриф директивы
`docs/brief-2026-10-04-archcom-founding.md`) и в истории репы; для
связности истории читай их вместе с этой спекой.
