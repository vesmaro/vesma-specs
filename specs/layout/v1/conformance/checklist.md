# Conformance checklist — layout v1

Гейт соответствия инсталляции контракту
[spec.md](../spec.md) (версия 1.0.0-draft.1). Тип проверки: **авт** —
исполняемая проверка (тест-пак движка / раннер conformance), **ручн** —
инспекция кода/артефактов. Контракт ратифицируется первым зелёным
прохождением всех пунктов реализацией в движке vesma. Пункт без покрытия =
реализация не конформана. На нумерацию LY-xx ссылается threat model спеки
(§8); doctor-проверки DR-xx — §3.10 спеки.

| ID | Требование | Проверка | Тип | Раздел спеки |
|---|---|---|---|---|
| LY-01 | Права config-корня: `~/.config/vesma/`, `components.d/`, `env/` — `0700`, владелец — пользователь супервайзера; права выставлены явно (не от umask) | тест: создание с «плохим» umask → stat каталогов 0700 | авт | §3.1, §3.2 |
| LY-02 | Drop-in `components.d/`: имя файла == `metadata.name`; install атомарно пишет (tmp + rename), uninstall удаляет; каждый файл каталога — валидный манифест (невалидный = fail-closed ошибка загрузки); env_file манифестов вне `components.d/` | тест: install/uninstall двух компонентов (чужие файлы не тронуты); фикс-манифест с невалидным соседом → отказ загрузки | авт | §3.5 + CM §3.1 |
| LY-03 | env-файлы: `env/<name>.env` — `0600`, владелец — пользователь; fail-closed загрузка: не `0600` / чужой владелец / объявлен и отсутствует = отказ старта с готовой командой исправления (`ENV_FILE_UNSAFE`) | тесты: старт с правами 0644, с чужим владельцем, с удалённым файлом → отказ + команда в диагностике | авт | §3.5 + CM §3.5 |
| LY-04 | Data-каталоги `~/.local/share/vesma/<name>/` — `0700`, владелец; default cwd ребёнка = `{data_dir}`; `cwd` манифеста по умолчанию — каноническое значение install-флоу | тест: spawn → `/proc/<pid>/cwd` == data-каталог; stat каталога | авт | §3.2, §3.4 |
| LY-05 | venv-уникальность: `venvs/<name>/` — `0700`, ровно один venv на python-юнит; два компонента на одном venv = ошибка install-валидации; in-process и не-python дети venv в `venvs/` не имеют | тест: инсталляция board (in-process) + worker (python-ребёнок) + mesh (go-ребёнок) → ровно один `venvs/worker`; скриптованный шаринг → ошибка | авт | §3.8 |
| LY-06 | venv integrity: site-packages не миро- и не группо-записываемы, владелец совпадает, `pip freeze` == lock (дрейф = FAIL) | тест: chmod 0777 site-packages → FAIL; ручная установка пакета → FAIL с командой | авт | §3.8, DR-02 |
| LY-07 | `PYTHONNOUSERSITE=1` безусловно в окружении каждого python-процесса (движок и дети); тест импорта в чистом окружении — user-site отсутствует в `sys.path` | conformance-ребёнок печатает своё окружение и `sys.path`; раннер сверяет (симметрично SL-13) | авт | §3.8, DR-03 |
| LY-08 | Пин-политика: зависимости `==` против lock; источники — только PyPI (прямой URL/wheel со стороны = ошибка); hash-pinning (`--require-hashes`) — дефолт (SHOULD), мандат v2 | проверка lock-файла install-флоу: все пины `==`, источники pypi.org; URL-зависимость → reject | авт | §3.8 |
| LY-09 | Единственность мест логов: systemd → только journald (маркировка `SYSLOG_IDENTIFIER=vesma-<component>` супервайзером); не-systemd → только `state/logs/<name>/`, ротация 10 MB × 5; других мест нет (не data, не config, не cache, не `/var/log/vesma`), двойная запись запрещена | тест A (systemd): отсутствие файловых логов + journalctl-фильтр находит строки; тест B (контейнер): ротация 10 MB × 5; скан инсталляции на «третьи места» | авт | §3.7 |
| LY-10 | history: `~/.local/state/vesma/history/` — `0700`, append-only (существующие записи не переписываются/не удаляются) | тест: переходы FSM дописывают в конец; попытка перезаписи середины → инвариант append-only | авт | §3.7 |
| LY-11 | Runtime: `${XDG_RUNTIME_DIR}/vesma/` — `0700`, `control.sock` — `0600`; пустой `XDG_RUNTIME_DIR` → fallback `state/run/` (`0700`) + WARN-строка; pid-файлы — только в runtime, не механизм single-instance | тест: старт с XDG_RUNTIME_DIR и с очищенным (путь + WARN); stat сокета; единственность pids | авт | §3.6 + CS §3 |
| LY-12 | Кэш: `~/.cache/vesma/<name>/` — `0750`; запись только через API записи движка; попытка записать значение из env-файла → отказ API; удаление кэша не меняет корректность инсталляции | тест: probe-запись значения env-файла через API → отказ; rm -rf кэша → компонент продолжает работать | авт | §3.9 |
| LY-13 | System-профиль: пути/права соответствуют таблице §3.3 (`/etc/vesma/vesma.yaml` и `components.d/` 0640 root:vesma, `env/<name>.env` 0600 root:vesma — единое правило с user-профилем, `/run/vesma/` 0750 root:vesma-oper, `control.sock` 0660); `/var/log/vesma` не создаётся | инспекция реализованных артефактов против таблицы | ручн | §3.3 |
| LY-14 | Doctor: все находки DR-01…DR-11 несут severity `OK/WARN/FAIL` и готовую команду исправления; doctor не исполняет команды сам; FAIL DR-01 на env-файле согласован с fail-closed стартом | тест: инжекция находок (0644 env, дрейф юнита) → в выводе команда; doctor не мутирует инсталляцию | авт | §3.10 |

Пункты system-профиля исполняются и чеклятся на горизонте v2 вместе с
реализацией (спека §3.3; реализация отложена за миграцию
легаси-развёртывания — не ранее закрытия первого окна наблюдения
учредительного трека). Прохождение user-пунктов LY-01…LY-12, LY-14
фиксируется реализацией в движке; отсюда берётся ратификация статуса
контракта `1.0.0`.
