# layout v2 — dual-profile лэйаут (user `~/.vesma` + system FHS)

> **Статус: draft (2.0.0-draft.1).** Форма контракта — dual-profile
> установка (user-профиль = канон/дефолт, system-профиль = FHS), единый
> декларативный FHS-манифест, механика `install --system`, doctor-гейты,
> сосуществование юнитов — ратифицирована АрхКомом VESMA 2026-10-21
> ([ADR-0045](https://github.com/vesmaro/vesma/blob/main/docs/project/adr/0045-dual-profile-fhs-layout.md)
> в репо движка) и здесь **кодифицируется, а не переигрывается**.
> Ратификация статуса stable — первая конформная реализация (волновой
> план — §7). Изменения после ратификации — только через SemVer-процесс.

Ключевые слова MUST / MUST NOT / SHOULD / MAY интерпретируются по RFC 2119.
Проза — русская; идентификаторы и пути — канонические (EN).

## 1. Scope

Лэйаут v2 фиксирует **dual-profile** дисциплину каталогов инсталляции VESMA:
выбор «на пользователя / глобально на систему» — продуктовый выбор
**первого класса**, совершаемый при установке, а не технический
дефолт. v1 закрывал инвентарный хаос легаси в user-профиле; v2 решает
следующую пару задач: (а) user-профиль становится **самодостаточным** в
`~/.vesma/**` — одно дерево, один юнит резервного копирования, удаления и
аудита (прецеденты: `~/.vscode`, `~/.nvm`); (б) system-профиль получает
полную FHS-реализацию — `/etc/vesma`, `/var/lib/vesma`, `/usr/lib/vesma`,
`/var/cache/vesma`, journald — для системных развертываний, контейнеров и
будущих deb/rpm-пакетов.

**В скоупе:**

- модель dual-profile и правило выбора профиля при установке (§3.1);
- user-профиль v2: самодостаточное дерево `~/.vesma/**`, полная таблица
  путей и прав, явный список исключений, мандатированных ОС (§3.2);
- legacy-генерация user-профиля v1.5 (XDG-россыпь v1): нормативный резолв
  по метке генерации, без ломки работающих установок (§3.3);
- system-профиль: полная таблица FHS-путей, прав и владельцев (§3.4);
- экосистемная таблица размещения: каждый артефакт экосистемы (движок,
  MCP-сервер/entrypoint, агенты-дети, board, metrics, mesh, таймеры)
  встроен в единую структуру обоих профилей; интеграционные поверхности в
  чужих харнесах — external (§3.5);
- расширение плейсхолдеров argv (§3.6);
- drop-in каталог манифестов, `env.d`, conffile-зона (§3.7);
- runtime и IPC, производные профиля: юниты user/system сосуществуют без
  префиксов (§3.8);
- единственность мест логов: journald — канон в обоих профилях;
  `/var/log/vesma` — opt-in system-профиля (§3.9);
- venv-дисциплина обоих профилей: один venv на python-юнит; в system —
  root-owned venv с атомарным symlink-swap-обновлением (§3.10);
- кэш: регенерируемое, никогда не секреты (§3.11);
- **один декларативный FHS-манифест** (пути/права/владельцы) — источник
  истины для инсталлятора, контейнера и будущих deb/rpm (§3.12);
- установка/обновление/удаление system-профиля: canonical
  `sudo vesma service install --system`, state-манифест установки →
  exact-inverse uninstall (§3.13);
- doctor-гейты v2: DR-14…DR-19 (§3.14);
- миграция: консолидация user-инсталляций v1.5 → v2 без ломки; резерв
  `migrate-store --target=system` (§9).

**Вне скоупа (домены соседних контрактов и будущих волн):**

- форма манифеста компонента и правила `env_file` —
  [specs/component-manifest/v1](../../component-manifest/v1/spec.md):
  лэйаут фиксирует **где**, манифест — **что**;
- поведение супервайзера, FSM, юнит-шаблон, hardening —
  [specs/service-lifecycle/v1](../../service-lifecycle/v1/spec.md);
- протокол сокета, TOCTOU, peer-аутентификация —
  [specs/control-socket/v1](../../control-socket/v1/spec.md): лэйаут
  фиксирует место и права;
- исполнение консолидации v1.5 → v2 и system-мовера — движок (волны
  плана ADR-0045); спека фиксирует целевые пути, семантику и гейты;
- deb/rpm-упаковка — будущая волна: тонкие обёртки над FHS-манифестом,
  собственной упаковочной логики не вводят (§3.12, §7);
- hash-pinning-мандат и lock-тулинг — отложены (наследование v1 §7);
- redaction секретов в пересылаемых строках — домен SL (v1 §7).

**Потребители:** движок `vesma` (install-флоу — единственный писатель
установки; супервайзер — читатель-исполнитель; doctor — проверяющий;
резолвер путей — единственный источник путей в коде), компоненты
(потребляют пути через плейсхолдеры), сборка контейнера (потребляет
FHS-манифест), будущие packagers deb/rpm, conformance-раннер
`tools/conformance`, внешние интеграторы.

## 2. Терминология

Термины Canonical layout, Runtime directory, venv discipline, Supervisor,
Component, Manifest определены в [глоссарии](../../../GLOSSARY.md) и здесь
не переопределяются. Контрактные термины v2:

| Термин | Значение |
|---|---|
| профиль установки | user (канон/дефолт, самодостаточный `~/.vesma/**`) или system (FHS, opt-in); выбор — продуктовое решение при установке, фиксируется установкой и виден doctor'у |
| генерация лэйаута | версия формы user-профиля конкретной инсталляции: `v1.5` (XDG-россыпь, [layout v1](../v1/spec.md)) или `v2` (самодостаточный `~/.vesma/**`); фиксируется меткой при установке/консолидации; резолвер путей опирается на метку, а не на «актуальный канон» |
| самодостаточный профиль | профиль, все артефакты которого живут в одном корневом дереве (`~/.vesma/**`); исключения — только точки, мандатированные ОС (явный список §3.2-a) |
| FHS-манифест | единственный декларативный файл путей/прав/владельцев system-профиля; источник истины для инсталлятора, сборки контейнера и будущих deb/rpm (§3.12) |
| conffile-зона | файлы, которые обновления (инсталлятор, будущие пакеты) не перезаписывают молча: операторская правка детектируется, сохраняется в backup, обновление не уничтожает её (§3.7) |
| install-state | state-манифест установки system-профиля — `/var/lib/vesma/install-state.yaml`: полный список созданного (юниты, файлы, venv-ревизии, sysusers-фрагмент); uninstall = точная инверсия (§3.13) |
| symlink-ревизия | форма venv в system-профиле: `venvs/<name>` — симлинк на `venvs/<name>-<rev>/`; обновление = атомарная подмена симлинка (§3.10) |
| IPC-каталог | каталог сокета и pids, производный профиля: user — `${XDG_RUNTIME_DIR}/vesma/`, system — `/run/vesma/` (§3.8) |
| консолидация | миграционный шаг v1.5 → v2 user-профиля: перенос venv/кэша (и сервисного стека) внутрь `~/.vesma`; не ломает работающую установку (§9.2) |
| external surface | интеграционная поверхность в чужом домене (mcp.json харнесов, строки в shell rc): лэйаут документирует её, но не владеет и не обслуживает (§3.5) |
| round-trip soak | период наблюдения полноцикловых прогонов (установка → работа → обновление → удаление → восстановление) на реальной машине до исполнения миграции прода (7-я опора product-grade стандарта) |
| doctor | диагностическая команда `vesma doctor --service`; реестр v1 DR-01…DR-13 + v2 DR-14…DR-19 (§3.14) |

## 3. Контракт

### 3.1 Профили и выбор профиля

- **MUST**: dual-profile — user и system; выбор профиля — явное решение
  при установке (первый класс), а не скрытый дефолт окружения.
- **MUST**: user-профиль — канон и дефолт: `vesma service install` без
  флагов ставит user-профиль; system ставится только явно:
  `sudo vesma service install --system` (§3.13).
- **MUST**: профиль инсталляции фиксируется установкой (метка профиля и
  генерации лэйаута) и читается резолвером, doctor'ом и CLI; тихое
  переключение профиля существующей инсталляции запрещено.
- **MUST**: user- и system-профили одной машины имеют **разные**
  data-root'ы; совмещение обоих профилей на одном data-root —
  конфигурационная ошибка, doctor → FAIL (DR-14; «ERROR» вердикта).
- **MAY**: оба профиля сосуществовать на одной машине (пользовательский
  стек пользователя + системный стек) — при разделе IPC и данных (§3.8,
  §3.4).
- **MUST**: пути резолвируются **только** резолвером движка от таблиц
  §3.2/§3.4 и метки генерации; хардкод путей вне резолвера — нарушение
  контракта.
- **MUST**: работающая инсталляция не меняет резолв путей без явного
  миграционного шага оператора (консолидация §9.2, system-мовер §9.3):
  смена канона не переписывает живые установки.

### 3.2 User-профиль v2 (самодостаточный `~/.vesma/**`, нормативный)

User-профиль v2 — одно дерево `~/.vesma/`, владелец — пользователь
супервайзера. Существующее содержимое `~/.vesma` (store-дом движка:
`vesma.db`, `data/`, `vault/`, `config.yaml`, `completion/`,
`logs/vesma.log` + аудит-журналы) остаётся как есть — таблица **не
переигрывает** store-дом движка (канон ADR-0044), а встраивает в то же
дерево сервисный стек.

Таблица MUST (корень `~/.vesma`, каталог `0700`, если не указано иное):

| Путь | Содержимое | Права |
|---|---|---|
| `~/.vesma/config.yaml` | общий конфиг; конфиг компонента = секция общего конфига (CM §3.9) | файл `0600` |
| `~/.vesma/components.d/<name>.yaml` | манифесты компонентов (drop-in; install кладёт, uninstall убирает) | каталог `0700` |
| `~/.vesma/env.d/<name>.env` | env-файлы секретов | файл `0600`; fail-closed загрузка (CM §3.5) |
| `~/.vesma/components/<name>/` | данные компонента; default cwd ребёнка; `config.schema.json` компонента (резолв `config.schema_file`, CM §3.9 — от data-каталога) | каталог `0700` |
| `~/.vesma/venv/` | venv движка (supervisor runtime): движок + in-process модули; единственный venv вне `venvs/` | каталог `0700` |
| `~/.vesma/venvs/<name>/` | venv python-компонента-ребёнка | каталог `0700` |
| `~/.vesma/logs/<name>/` | файловые логи (режим files-under-state, §3.9); ротация 10 MB × 5 | каталог `0700` |
| `~/.vesma/history/` | журнал переходов супервайзера (append-only) | каталог `0700` |
| `~/.vesma/run/` | fallback runtime (сокет, pids) при пустом/непригодном `XDG_RUNTIME_DIR` + WARN | каталог `0700` |
| `~/.vesma/cache/<name>/` | регенерируемое; НИКОГДА не секреты (§3.11) | каталог `0750` |
| `${XDG_RUNTIME_DIR}/vesma/` | канонический runtime: `control.sock` `0600`, pids | каталог `0700` |

Примечания:

- **a. Исключения, мандатированные ОС** (полный список; всё прочее —
  внутри `~/.vesma`):
  1. **systemd user unit dir** — `~/.config/systemd/user/`: systemd
     читает юниты только оттуда. Канон-хранение юнита —
     `~/.vesma/systemd/user/vesma.service`; install-флоу размещает в
     systemd-каталог копию/симлинк и обновляет `daemon-reload`. Дрейф
     «канон ↔ установленный» ловит doctor (DR-18).
  2. **`${XDG_RUNTIME_DIR}/vesma/`** — сокеты обязаны жить в runtime-FS
     (tmpfs-семантика); fallback `~/.vesma/run/` + WARN — правило v1
     (control-socket v1 §3), сохранено.
  3. **строки в shell rc** (подключение completion) — внешняя поверхность
     (external surface): документируется, не обслуживается лэйаутом.
  4. **journald** — канонический приёмник логов при systemd (служба ОС,
     не путь).
- **b.** XDG-переменные (`XDG_CONFIG_HOME`, `XDG_DATA_HOME`,
  `XDG_STATE_HOME`, `XDG_CACHE_HOME`) в резолве user-профиля v2 **не
  участвуют**; единственная XDG-переменная профиля — `XDG_RUNTIME_DIR`
  (п. a.2).
- **c.** Права выставляются явно при создании (не от umask); каталог,
  права которого ослаблены относительно таблицы, — fail-closed для
  соответствующей операции (правило v1 §3.1 сохранено).
- **d.** Дерево store-дома движка (`data/`, `vault/`, `logs/` верхний
  уровень, `vesma.db`) — домен канона ADR-0044; компонентные подкаталоги
  `logs/<name>/` не пересекаются с файлами движка в `logs/`.
- **e.** Имена компонентов валидируются против **реестра
  зарезервированных имён дерева**: `venv`, `venvs`, `components`,
  `components.d`, `env.d`, `cache`, `logs`, `history`, `run`, `completion`,
  `systemd`, `data`, `vault`, `install-state.yaml`; коллизия = отказ
  install-валидации (механизм v1 §3.8 расширен аддитивно; реестр MAY
  пополняться минорной версией).
- **f.** `venvs/<name>/` — только для python-компонентов-детей; in-process
  компоненты живут на venv движка; не-python дети venv не имеют (правило
  v1 §3.8 сохранено).

### 3.3 User-профиль v1.5 (legacy-генерация, нормативен для существующих установок)

- **MUST**: инсталляции, установленные в форме [layout v1](../v1/spec.md)
  (генерация `v1.5` — XDG-россыпь `~/.config/vesma`, `~/.local/share/
  vesma`, `~/.local/state/vesma`, `~/.cache/vesma`), продолжают резолвить
  пути по таблицам v1 до исполнения консолидации (§9.2): смена канона не
  ломает работающие установки (zero-regression; pin-тесты обеих генераций
  — волна 1 плана ADR-0045).
- **MUST**: новые user-инсталляции создаются только в форме v2 (§3.2).
- **MUST NOT**: движок не пишет в v1.5-пути инсталляции v2-генерации и
  наоборот; смешанная запись (часть артефактов в v1.5-, часть в v2-местах
  одной инсталляции) — дрейф, doctor → FAIL (DR-17).
- **SHOULD**: doctor помечает v1.5-инсталляцию advisory-находкой (DR-19)
  с готовой командой консолидации.

### 3.4 System-профиль (FHS, нормативный)

System-профиль — для глобальных развертываний: выделенный сервисный
аккаунт, системные юниты, пакетная дисциплина. Корневые решения:

- сервисный аккаунт `vesma:vesma` создаёт sysusers.d-фрагмент
  (системный пользователь, shell-вход запрещён, home `/var/lib/vesma`);
- конфигурация принадлежит root, читается группой `vesma`; секреты
  (`env.d`) — `0600`, group/world-чтение исключено;
- переменные данные (включая store-дом движка) — `/var/lib/vesma`;
- код (venv) — `/usr/lib/vesma`, статика дистрибутива — `/usr/share/
  vesma`; рантайм в эти деревья не пишет.

Таблица MUST:

| Путь | Содержимое | Права/владелец |
|---|---|---|
| `/etc/vesma/` | корень конфигурации | каталог `0750 root:vesma` |
| `/etc/vesma/config.yaml` | общий конфиг (CM §3.9) | файл `0640 root:vesma`; conffile-зона |
| `/etc/vesma/components.d/<name>.yaml` | манифесты компонентов (drop-in) | файл `0640 root:vesma`; conffile-зона; каталог `0750 root:vesma` |
| `/etc/vesma/env.d/<name>.env` | env-файлы секретов | файл `0600 root:vesma`¹; каталог `0750 root:vesma` |
| `/usr/lib/sysusers.d/vesma.conf` | sysusers-фрагмент: user+group `vesma` | файл `0644 root:root` |
| `/etc/systemd/system/vesma.service` | system-юнит супервайзера (генерируется install-флоу) | файл `0644 root:root` |
| `/usr/lib/vesma/venv/` | venv движка; symlink-ревизии (§3.10) | дерево `0755 root:root`; site-packages не группо-/миро-записываемы |
| `/usr/lib/vesma/venvs/<name>` | venv python-компонента; симлинк на ревизию `<name>-<rev>/` | как выше |
| `/usr/share/vesma/` | статика дистрибутива: бандл-манифесты, конфиг-схемы, шаблоны юнитов, completion | каталоги `0755 root:root`, файлы `0644 root:root`; рантайм — только чтение |
| `/var/lib/vesma/` | корень данных: store-дом движка (vesma.db, `data/`, `vault/`) + данные компонентов | каталог `0750 vesma:vesma` |
| `/var/lib/vesma/vesma.db` | БД store движка | файл `0600 vesma:vesma` |
| `/var/lib/vesma/<name>/` | данные компонента; default cwd ребёнка | каталог `0750 vesma:vesma`; файлы БД и секрето-подобные — `0600` |
| `/var/lib/vesma/history/` | журнал переходов супервайзера (append-only) | каталог `0750 vesma:vesma` |
| `/var/lib/vesma/install-state.yaml` | state-манифест установки (exact-inverse uninstall, §3.13) | файл `0640 root:vesma`; писатель — install-флоу |
| `/var/cache/vesma/<name>/` | регенерируемое, никогда не секреты (§3.11) | каталог `0750 vesma:vesma` |
| `/var/log/vesma/<name>/` | файловые логи — **только opt-in** (§3.9) | каталог `0750 vesma:vesma`; без opt-in не создаётся |
| `/run/vesma/` | IPC: `control.sock`, pids | `RuntimeDirectory=vesma`, `RuntimeDirectoryMode=0750`; владелец — `User=`/`Group=` юнита; сокет — control-socket v1 §3 |

¹ Владелец `env.d`-файлов — сервисный аккаунт, от имени которого читает
супервайзер (дизайн-дефолт `root:vesma`; финальная фиксация — волна юнитов
плана ADR-0045). Инвариант нормативен: `0600`, group/world-чтение
исключено, читать может только сервисный аккаунт супервайзера; любой
дрейф — doctor FAIL (DR-15), загрузка fail-closed (CM §3.5).

Примечания:

- **a.** Отображение ролей user → system (принцип 1:1 v1 сохранён там,
  где ОС не мандатирует иное): конфигурация `~/.vesma` → `/etc/vesma`;
  данные/состояние `~/.vesma` → `/var/lib/vesma`; код (venv) `~/.vesma` →
  `/usr/lib/vesma`; статика (в user — внутри wheel) → `/usr/share/vesma`;
  логи-файлы → `/var/log/vesma` (opt-in); runtime → `/run/vesma`.
- **b.** Группа `vesma-oper` из дизайн-таблицы v1 §3.3 **не вводится**;
  групповой доступ оператора к system-сокету — открытый вопрос волны
  юнитов (реестр ADR-0045); до решения доступ к system-IPC — root.
- **c.** `/var/log/vesma` в user-профиле не существует ни в какой форме;
  в system — только opt-in (§3.9).

### 3.5 Экосистемная таблица размещения

Каждый артефакт экосистемы встроен в единую структуру обоих профилей.
Классы рантайма: движок и in-process компоненты — venv движка;
python-дети — собственный venv; не-python дети — исполняемый файл/бинт
без venv; таймеры — systemd timer-юниты (зона ОС §3.2-a).

| Артефакт экосистемы | Класс | user (v2) | system |
|---|---|---|---|
| движок `vesma` (супервайзер, API, MCP-сервер/entrypoint) | in-process (venv движка) | `~/.vesma/venv/` | `/usr/lib/vesma/venv/` |
| python-компонент-ребёнок (напр. worker-класс) | venv компонента | `~/.vesma/venvs/<name>/` | `/usr/lib/vesma/venvs/<name>` (symlink-ревизии) |
| не-python компонент-ребёнок (напр. mesh-класс) | бинарь без venv | внутри venv движка / бандла | `/usr/share/vesma/` (статика) |
| board, metrics (in-process бандл) | in-process | `~/.vesma/venv/` | `/usr/lib/vesma/venv/` |
| агенты-дети (по манифестам) | по классу ребёнка | слоты таблиц §3.2 | слоты таблиц §3.4 |
| манифест компонента | конфигурация | `~/.vesma/components.d/<name>.yaml` | `/etc/vesma/components.d/<name>.yaml` |
| общий конфиг | конфигурация | `~/.vesma/config.yaml` | `/etc/vesma/config.yaml` |
| env-секреты компонента | секреты | `~/.vesma/env.d/<name>.env` | `/etc/vesma/env.d/<name>.env` |
| данные компонента | данные | `~/.vesma/components/<name>/` | `/var/lib/vesma/<name>/` |
| state супервайзера (history) | данные | `~/.vesma/history/` | `/var/lib/vesma/history/` |
| логи (journald-канон; файловый режим) | логи | `~/.vesma/logs/<name>/` (files-under-state) | journald primary; `/var/log/vesma/<name>/` — opt-in |
| кэш компонента | кэш | `~/.vesma/cache/<name>/` | `/var/cache/vesma/<name>/` |
| сокет и pids | IPC | `${XDG_RUNTIME_DIR}/vesma/` | `/run/vesma/` |
| юнит супервайзера | юнит ОС | канон `~/.vesma/systemd/user/vesma.service` → `~/.config/systemd/user/` (§3.2-a.1) | `/etc/systemd/system/vesma.service` |
| timer-юниты (напр. self-update) | юнит ОС | `~/.config/systemd/user/` (канон в `~/.vesma/systemd/user/`) | `/etc/systemd/system/` |
| статика дистрибутива (бандл-манифесты, схемы) | поставка | внутри wheel (`importlib.resources`) | `/usr/share/vesma/` |
| completion | поставка | `~/.vesma/completion/` (rc-строка — external) | `/usr/share/vesma/completion/` (rc-строка — external) |
| интеграции в чужих харнесах (mcp.json харнеса) | **external surface** | вне дерева; документируется, не обслуживается | вне дерева; документируется, не обслуживается |

- **MUST**: компонент не хардкодит своё размещение — получает пути через
  плейсхолдеры (§3.6) и канонические слоты таблиц; новая сущность
  экосистемы встраивается таблицей (аддитивная правка, минорная версия).
- **MUST**: external-поверхности не обслуживаются лэйаутом: создание
  записей в чужих доменах (mcp.json, shell rc) — домен соответствующего
  интеграционного флоу движка; лэйаут фиксирует только то, что записи
  указывают на канонические пути этого контракта.

### 3.6 Расширение плейсхолдеров argv

Плейсхолдеры манифеста (allowlist — CM §2) расширяет супервайзер при
spawn по таблице MUST:

| Плейсхолдер | User (v2) | System |
|---|---|---|
| `{config_path}` | `~/.vesma/config.yaml` | `/etc/vesma/config.yaml` |
| `{data_dir}` | `~/.vesma/components/<name>/` | `/var/lib/vesma/<name>/` |
| `{runtime_dir}` | `${XDG_RUNTIME_DIR}/vesma/` (fallback `~/.vesma/run/`) | `/run/vesma/` |
| `{venv_bin}` | `~/.vesma/venvs/<name>/bin` | `/usr/lib/vesma/venvs/<name>/bin` (через symlink-ревизию) |

- **MUST**: других подстановок нет — никакого shell, никакой интерполяции
  окружения (CM §3.5); расширение выполняет супервайзер.
- **MUST**: `{venv_bin}` у компонента без venv не расширяется; ссылка на
  `{venv_bin}` без venv = отказ старта (fail-closed).
- **MUST**: для legacy-генерации v1.5 плейсхолдеры расширяются по таблице
  v1 §3.4 (метка генерации, §3.3).

### 3.7 Каталог манифестов, env.d и conffile-зона

- **MUST**: каталог манифестов = `components.d/` профиля (§3.2/§3.4);
  имя файла == `metadata.name`; каждый файл каталога обязан быть валидным
  манифестом — невалидный = fail-closed ошибка загрузки (правило v1
  §3.5 сохранено).
- **MUST**: drop-in дисциплина: install атомарно создаёт/обновляет файл
  (tmp + rename), uninstall удаляет; единственный писатель — install-флоу.
- **MUST (conffile-зона)**: `config.yaml` и `components.d/` обоих
  профилей — conffile-зона: обновление (инсталлятор, будущий пакет) не
  перезаписывает файл с операторской правкой молча; расхождение
  детектируется, правка сохраняется в backup (дисциплина
  `.pre-regen.bak` движка), оператор получает явный выбор. Будущие
  deb/rpm обязаны объявлять эти пути conffiles своего пакетного формата.
- **MUST**: env-файлы — `env.d/<name>.env` профиля, файл `0600`,
  fail-closed загрузка (не `0600` / чужой владелец / объявлен и
  отсутствует = отказ старта с готовой командой исправления; CM §3.5,
  `ENV_FILE_UNSAFE`); в system-профиле дрейф прав env.d — doctor FAIL
  (DR-15, гейт вердикта).
- **MUST**: install-флоу размещает создаваемые env-файлы только в
  `env.d/<name>.env`.

### 3.8 Runtime, IPC и сосуществование юнитов

- **MUST**: юниты user/system сосуществуют **без префиксов**: оба
  называются `vesma.service` в своих областях systemd
  (`~/.config/systemd/user/` и `/etc/systemd/system/`); различение —
  областью systemd, не именем.
- **MUST**: IPC производен профиля: user — `${XDG_RUNTIME_DIR}/vesma/`
  (`0700`, fallback `~/.vesma/run/` + WARN), system — `/run/vesma/`
  (`RuntimeDirectory=vesma`, `RuntimeDirectoryMode=0750`).
- **MUST**: сокет-артефакты подчинены control-socket v1 целиком
  (TOCTOU/SYMLINK-процедура, peer-аутентификация, запрет TCP); лэйаут
  фиксирует место и права.
- **MUST**: CLI-команды, затрагивающие оба профиля, явно различают
  профили; дефолт — user; механика флага — реализация движка.
- **MUST NOT**: постоянное состояние в IPC-каталоге не размещается
  (tmpfs-семантика; правило v1 §3.6 сохранено).

### 3.9 Логи и журнал переходов

- **MUST** (канон при systemd, оба профиля): всё в journald; маркировку
  `SYSLOG_IDENTIFIER=vesma-<component>` выполняет супервайзер (SL §3.4);
  `vesma service logs` = journalctl-фильтр, не grep по файлам.
- **MUST** (user, контейнер/ручной режим): files-under-state —
  `~/.vesma/logs/<name>/`, ротация 10 MB × 5.
- **MUST** (system): `/var/log/vesma/<name>/` — **opt-in**: файловые
  логи создаются только при явном включении оператором; по умолчанию —
  только journald. Opt-in не включает двойную запись: режим ровно один.
- **MUST NOT**: никаких «третьих мест» логов; двойная запись в оба места
  запрещена (правило v1 §3.7 сохранено).
- **MUST**: history — append-only, путь по таблицам (§3.2/§3.4);
  содержимое — структурные строки (SL §3.4).

### 3.10 venv-дисциплина

Оба профиля наследуют правила v1 §3.8: один управляемый venv на
python-юнит; два компонента на одном venv = ошибка; `PYTHONNOUSERSITE=1`
безусловно в каждый python-процесс; зависимости пинуются точно (`==`)
против lock; источники — только PyPI; site-packages не миро- и не
группо-записываемы; ручной `pip install` в управляемый venv = freeze-дрейф
(DR-02). Профильные дополнения:

- **MUST** (user): venv-дерево — `~/.vesma/venv/` (движок) и
  `~/.vesma/venvs/<name>/` (дети), `0700`, владелец — пользователь.
- **MUST** (system): venv принадлежит root (`/usr/lib/vesma/venv`,
  `/usr/lib/vesma/venvs/<name>`), дерево `0755 root:root`; запись в
  рантайме исключена (модифицирует только install-флоу от root).
- **MUST** (system): venv компонента — **symlink-ревизия**:
  `<name>-<rev>/` — материализованная ревизия (имя ревизии — контент-id
  установки), `venvs/<name>` — симлинк на активную ревизию; обновление =
  атомарная подмена симлинка (tmp + rename), старая ревизия удаляется
  только после успешного swap и проверки живости.
- **MUST** (system): venv материализует установщик: `uv venv` + установка
  **wheel той же сборки**, из которой работает установщик; `sudo pip` /
  pip-as-root запрещены.
- **MUST** (system): симлинк ревизии резолвится внутри собственного
  корня (`/usr/lib/vesma/venvs/`); симлинк наружу — doctor FAIL (DR-16).

### 3.11 Кэш

- **MUST**: `cache/<name>/` профиля (`~/.vesma/cache/<name>/` `0750`;
  `/var/cache/vesma/<name>/` `0750 vesma:vesma`) — только регенерируемое
  содержимое; удаление в любой момент не меняет корректность инсталляции.
- **MUST**: кэш НИКОГДА не содержит секреты; enforcement — taint-API
  записи движка (правило v1 §3.9, LY-12 сохранено).
- **MUST NOT**: конфиги, манифесты, env-содержимое, логи и state-данные в
  кэше не размещаются.

### 3.12 FHS-манифест — единый источник истины путей

- **MUST**: существует **один** декларативный манифест FHS-путей
  (поставляется дистрибутивом движка), перечисляющий каждый путь
  system-профиля и соответствие user-профилю: поля минимум — `role`
  (семантическая роль строки таблиц §3.2–§3.5), `user_path`,
  `system_path`, `mode`, `owner`, `group`, `flags` (например
  `conffile`, `opt-in`, `symlink-revision`).
- **MUST**: потребители манифеста: инсталлятор `install --system`,
  сборка контейнера, будущие deb/rpm-упаковки; каждый из них строит
  артефакты из манифеста, а не из собственных списков путей.
- **MUST**: в коде движка пути system-профиля резолвируются только через
  манифест (резолвер); дублирование путей в коде/юнитах/скриптах мимо
  манифеста — нарушение контракта (DR-15 сверяет юнит и дерево с
  манифестом).
- **MAY**: оператор переопределять базу размещения (например `/opt/
  vesma`-форма) явным override-механизмом манифеста; override валидируется
  при установке и проверяется doctor'ом; непроверенный override = WARN.
- **MUST**: форма сериализации — YAML; схема полей фиксируется примером
  `examples/example-fhs-manifest.yaml` этого контракта; сужение/переименование
  полей = MAJOR.

### 3.13 Установка, обновление, удаление (system-профиль)

- **MUST**: канонический установщик system-профиля — `sudo vesma service
  install --system`; установка идемпотентна (повторный запуск — no-op
  или явный refresh, без дублирования артефактов).
- **MUST**: установщик создаёт сервисный аккаунт через sysusers.d-фрагмент
  (idempotent: повторный запуск не дублирует аккаунт).
- **MUST**: установщик ведёт install-state (`/var/lib/vesma/
  install-state.yaml`): каждый созданный артефакт (юнит, файл, venv-ревизия,
  sysusers-фрагмент, каталог) фиксируется записью до/при создании.
- **MUST**: uninstall (`sudo vesma service uninstall --system`) — точная
  инверсия install-state: удаляются только записанные артефакты, в
  обратном порядке; чужие файлы не трогаются; дрейф «state ↔ файловая
  система» = громкий отказ с предложением doctor (DR-17), а не тихий
  пропуск.
- **MUST**: обновление system-профиля — mode-aware: новая ревизия venv
  материализуется рядом, симлинк подменяется атомарно, предыдущая ревизия
  удаляется после успешного swap + health-проверки (4-я опора
  product-grade стандарта).
- **MUST NOT**: установщик system-профиля не запускает `pip` от root
  (§3.10) и не пишет в чужие venv (изоляция окружений — глобальное
  правило 8 владельца).

### 3.14 Doctor-гейты v2 (`vesma doctor --service`)

Реестр v1 (DR-01…DR-13) действует для user-профиля с точностью до путей
генерации (§3.3). v2 добавляет:

| ID | Проверка | Подробности |
|---|---|---|
| DR-14 | изоляция data-root профилей | user- и system-профили на одном data-root (пересечение корней данных/конфигурации) = FAIL («ERROR» вердикта) + команда исправления |
| DR-15 | права system-профиля | сверка дерева с FHS-манифестом: `/etc/vesma` `0640/0750 root:vesma`, `env.d` `0600` (дрейф = FAIL — гейт вердикта), `/var/lib/vesma` `0750 vesma:vesma`, БД `0600`, кэш/логи `0750`; юнит соответствует манифесту |
| DR-16 | venv-ревизии system | симлинк `venvs/<name>` резолвится внутри `/usr/lib/vesma/venvs/`, цель root-owned, не группо-/миро-записываема; `freeze` == lock активной ревизии; осиротевшие ревизии — WARN |
| DR-17 | install-state ↔ файловая система | сухая инверсия state-манифеста: каждый артефакт на месте, чужих вторжений в canonical-корни нет; дрейф = FAIL (system) / FAIL (user: смешение генераций §3.3) |
| DR-18 | дрейф юнитов обоих профилей | установленный юнит == канону (`~/.vesma/systemd/user/`, `/etc/systemd/system/`) == регенерированному install-флоу; расхождение = FAIL + команда |
| DR-19 | генерация лэйаута user-профиля | v1.5-инсталляция: advisory (INFO/WARN) с готовой командой консолидации; смешанное дерево = FAIL (DR-17) |

- **MUST**: каждая находка несёт severity `OK`/`WARN`/`FAIL` и готовую
  команду исправления с реальным путём; doctor не исполняет команды сам
  (правила v1 §3.10 сохранены).

## 7. Совместимость

- **SemVer**: `2.0.0-draft.1`; ратификация реализацией → `2.0.0` stable.
  Версия MAJOR: таблица user-профиля перерисована (XDG-россыпь →
  самодостаточный `~/.vesma`), имя общего конфига выровнено с каноном
  движка (`vesma.yaml` v1 → `config.yaml`), каталог env переименован
  (`env/` → `env.d/`), system-таблица v1 §3.3 заменена полной (venvs →
  `/usr/lib/vesma`, `/var/log/vesma` MUST NOT → opt-in, `vesma-oper` не
  вводится). Ломающее legitimизовано MAJOR-бампом (breaking-детектор CI).
- **Непрерывность deployed-установок**: метка генерации (§3.1, §3.3)
  сохраняет резолв работающих v1.5-инсталляций; переход — только явной
  консолидацией (§9.2). Это условие включения MAJOR: «ломает» контракт,
  не ломает работающие установки.
- **Спека v1**: каталог `v1/` неизменяем (ADR-0001 §2); при ратификации
  v2 контракту v1 присваивается `deprecated(v1→v2)` с окном по правилу
  ADR-0001 §2 (решение об окне — акт ратификации, не этой волны).
- **Потребители**: CM (`env_file` → `env.d/`, плейсхолдеры §3.6), SL
  (`ReadWritePaths` от таблиц, юнит-пути §3.8), control-socket (IPC-пути
  §3.8); правки примеров/прозы соседних спек — отдельные аддитивные PR,
  этот контракт их не исполняет.
- **Отложено (наследовано v1 §7)**: hash-pinning-мандат и lock-тулинг;
  redaction секретов в пересылаемых строках (SL §6).

## 8. Threat model (мини-STRIDE)

**Ассеты** (наследуются v1 §8): env-файлы секретов; venv как supply chain;
данные компонентов и store движка; history; кэш. **Новые v2-ассеты**:
install-state (подмена → неверный uninstall); симлинки venv-ревизий;
само дерево `~/.vesma` как единый приватный контур пользователя.

**Граница контракта:** файловая система лэйаута ↔ супервайзер / загрузчик
/ install-флоу / doctor; в system-профиле — граница root ↔ сервисный
аккаунт (DAC).

| Категория | Угроза | Митигация | Проверка |
|---|---|---|---|
| **I**nformation Disclosure | lax-права env.d/конфига (оба профиля) | env.d `0600` + fail-closed загрузчик; `/etc/vesma` `0640/0750 root:vesma`; `~/.vesma` `0700` | LY-01/LY-03, SY-03 |
| **I**nformation Disclosure | секреты в кэше | taint-API записи; кэш `0750` | LY-12 |
| **I**nformation Disclosure | логи в неучтённых местах | единственность мест; `/var/log/vesma` — opt-in system, в user запрещён | LY-09, SY-06 |
| **T**ampering | подмена venv (supply chain) | user: `0700`, владелец; system: root-owned, дерево `0755 root:root`, tamper требует root; freeze == lock | LY-05/LY-06, SY-07 |
| **T**ampering | симлинк venv-ревизии наружу (подмена кода через link) | симлинк обязан резолвиться внутри собственного корня | DR-16, SY-07 |
| **T**ampering | подмена install-state → uninstall удаляет/оставляет не то | state пишет только install-флоу (`0640 root:vesma`); uninstall при дрейфе — громкий отказ; удаляются только записанные артефакты | DR-17, SY-09 |
| **T**ampering | тихая перезапись операторских конфигов обновлением | conffile-зона: правка детектируется, backup + явный выбор | SY-05 |
| **E**levation of Privilege | user-site утечка; два компонента на одном venv | `PYTHONNOUSERSITE=1`; один venv на юнит (наследовано v1) | LY-07, DR-03/04 |
| **E**levation of Privilege | pip-as-root / запись в чужие venv | venv материализует `uv venv` + wheel той же сборки; чужие venv отвергаются | SY-08 |
| **D**enial of Service | переполнение диска логами/кэшем | ротация 10 MB × 5; кэш регенерируем; DR-10 (наследован) | LY-09, DR-10 |
| **R**epudiation | «кто изменил установку?» | единственный писатель — install-флоу; install-state append/update; history append-only; journald | SY-09, операционный контроль |
| **S**poofing | подмена на пути сокета | «trust boundaries: нет» — домен control-socket v1 §5; IPC-каталоги профилей изолированы (`/run/vesma` vs user runtime) | чеклист control-socket v1, DR-14 |

Каждая митигация закрыта conformance-чеком либо помечена «операционный
контроль» — тихих непроверяемых обещаний нет.

## 9. Миграция

### 9.1 Легаси (наследовано v1 §9)

Таблица «легаси-путь → канонический путь» v1 §9 действует для v1.5-формы;
порядок (инвентарь doctor → перенос → зелёный конформанс → утилизация
легаси-механизмов) и ограничение founding-окна сохранены. Целевые пути
v1-таблицы читаются в v2-канон через §3.2 (консолидация ниже).

### 9.2 Консолидация user-инсталляций v1.5 → v2

- **MUST**: консолидация — явный миграционный шаг оператора, не
  побочный эффект обновления; кандидат-носитель — расширение
  `vesma self-update apply` / `vesma service install` (выбор за волной
  мовера плана ADR-0045).
- **MUST**: порядок: doctor-инвентарь → остановка стека → перенос
  артефактов по таблице соответствия (venv → `~/.vesma/venv|venvs/`, кэш →
  `~/.vesma/cache/`, сервисный стек `components.d`/`env.d`/`components/`
  внутрь `~/.vesma/`) → простановка метки генерации v2 → зелёный doctor.
  Перенос — move с проверкой, удаление источника только после зелёной
  проверки (дисциплина ADR-0044: staging → verify → publish).
- **MUST**: работающая без консолидации v1.5-инсталляция продолжает
  работать (§3.3): консолидация не ломает, а переводит.
- **MUST NOT**: консолидация не трогает store-дом движка (`vesma.db`,
  `data/`, `vault/`, `config.yaml` — уже в `~/.vesma`) и external-поверхности
  (mcp.json, shell rc — только перегенерация указателей их собственными
  флоу).

### 9.3 Миграция прода в system-профиль — НЕ сейчас

- **MUST NOT**: исполняемая миграция существующего прода в system-профиль
  не входит в эту волну и не запускается без отдельного слова владельца.
- **MUST**: `vesma migrate-store` резервирует расширение `--target=system`
  (цель — перенос store-дома и сервисного стека в FHS-деревья §3.4);
  контракт цели — предмет отдельной ратификации при активации.
- **MUST**: precondition активации — round-trip soak system-профиля
  (полнодисковые циклы install → run → update → uninstall → restore на
  реальной машине; 7-я опора product-grade стандарта).
