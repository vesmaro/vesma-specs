# Conformance checklist — decision-provider v1

Человеческий чеклист соответствия **реализации провайдера** контракту
`specs/decision-provider/v1/spec.md` (версия 1.0.0-draft.2). Исполняемого
сьюта v1 нет — машинная форма интерфейса не заморожена (spec §6, §7); гейт
участия реализации в продуктовых решениях — зелёный чеклист + калибровочный
отчёт canon (spec §3.6). Способы проверки даны для интегратора и ревьюера
движка.

| ID | Пункт | Раздел спеки | Способ проверки |
|---|---|---|---|
| DP-01 | Точки решений движка программируются против интерфейса провайдера; прямых вызовов реализаций в обход интерфейса нет; смена провайдера — конфигурацией | §3.1 | код-ревью точек вызова; тест: переключение провайдера конфигом без правок кода потребителей |
| DP-02 | Реализация отвечает ровно тремя примитивами (`Choice`, `Score`, `Noul`); ответы типизированы (вариант/значение шкалы/да-нет + уверенность), свободный текст ответом не является | §3.2 | контрактные тесты примитивов на фиксированных входах |
| DP-03 | Провайдер не генерирует и не переписывает тела записей памяти | §3.2 | код-ревью; тест: тело записи до и после вызова байт-в-байт |
| DP-04 | Вход — только подготовленное canon-состояние (конверт + тела выбранных записей под запрос); сырых дампов памяти нет | §3.4 | код-ревью сборки входа; тест: вход содержит только выбранные записи запроса |
| DP-05 | Приватность-гейт: `no-federate`/секреты не покидают хранилище; записи с `no-federate` исключаются из подготовленного состояния до сборки запроса и до сканирования (сборка состояния — первая линия, скан — вторая); перед каждым внешним вызовом — механический скан (детекторы движка), находка любого класса останавливает вызов целиком; отказ/исключение/таймаут самого сканера прерывает внешний вызов с классом действия `call-class` — сканер fail-closed | §3.5 | тест: фикстура с секретом/`no-federate`-записью → внешнего вызова нет, warn класса `call-class`; тест: отказ сканера → внешний вызов прерван (fail-closed), warn класса `call-class` |
| DP-06 | Калибровочный гейт: не-базовая реализация (b)/(c) не участвует в продуктовых решениях до калибровки по методологии canon (vitals); льготы за локальность нет; «уверенность» некалиброванного не потребляется как число; каждая реализация документирует свою шкалу confidence (количественная шкала контрактом не фиксирована, кросс-реализационное сравнение чисел запрещено); на baseline (a) `deterministic` гейт не распространяется — она сама база калибровки и эталон честного замера | §3.6 | сверка с отчётом калибровки canon; конфиг-тест: некалиброванная реализация не активируется; ревью: шкала confidence задокументирована в документации реализации |
| DP-07 | Fail-open: дефект загрузки/пина → провайдер целиком деградирует к `deterministic`; отказ инференса на запросе → одиночный вердикт деградирует к детерминированному правилу; продуктовый путь (инжест, дедупликация) не блокируется ни при каком отказе | §3.8 | тест: подмена/повреждение артефакта → инжест продолжает работу; тест: отказ инференса → вердикт baseline-правила |
| DP-08 | Каждая деградация логируется машинно-парсируемо: код из пространства имён реализации (прецедент `CORTEX-E-*`) + класс действия из фиксированного контрактом множества (`provider-class` / `verdict-class` / `call-class`); литеральные токены действий — пространство имён реализации | §3.8 | тест: парсинг warn-строк при трёх классах отказа |
| DP-09 | Каждый ответ логируется машинно-парсируемо: примитив, реализация, уверенность; по журналу отвечается «кто принял решение» без чтения кода | §3.9 | тест: телеметрия на каждый вызов; ревью формата строки |
| DP-10 | Дефолтная реализация — `deterministic`; без явной конфигурации не-базовая не активируется | §3.7 | тест: чистый конфиг → отвечает baseline; проверка атрибуции в телеметрии |
| DP-11 | Внешний адаптер выключен по умолчанию; включение требует флага владельца **и** API-ключа; флаг без ключа или ключ без флага не активируют адаптер (отказ с классом `-CONFIG`) | §3.7, §4 | тесты: три комбинации гейта; скан исходящих соединений выключенного адаптера |
| DP-12 | Локальные реализации (a)/(b) без исходящего трафика по построению; веса несут fingerprint в отчёте прогона; смена весов = событие перекалибровки (несовпадение пина — громкий отказ загрузки, не тихая подмена) | §3.7, §3.8 | AST-тест на сетевые импорты (прецедент движка); тест: несовпадение fingerprint → `-PIN`-отказ |
| DP-13 | Freeze форматов не задет: интерфейс потребляет canon-записи как есть; конверт, типы, секции и схемы не меняются | §3.11 | сверка с пином canon-схем движка; тест: запись до/после прохождения через интерфейс |
| DP-14 | Политика (вопросы, критерии `Choice`, шкалы `Score`) инвариантна к смене провайдера и живёт в коде/конфиге продукта | §3.3 | тест: одинаковые входы при двух реализациях → одинаковый вопрос; ревью отсутствия политики в API провайдера |
| DP-15 | Провайдер — in-process интерфейс движка: манифест компонента не заводится, супервайзером не управляется, сетевого слушателя не открывает | §3.10 | тест: отсутствие слушателей у процесса движка; отсутствие манифеста в установке |

Прохождение: все пункты зелёные + калибровочный отчёт canon для не-базовых
реализаций (гейт §3.6). Статус контракта — `draft` до первой конформной
реализации в движке vesma (ратификация реализацией, ADR-0001 §2).
