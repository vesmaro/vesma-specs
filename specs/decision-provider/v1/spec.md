# decision-provider v1 — контракт провайдера решений («семантический if»)

> **Статус: draft.** Living-версия интерфейса мигрирована из vesma-canon
> ADR-0004 (2026-10-04, фаза 2 роадмапа vesma-specs); canon сохраняет
> историю и указатель. Решения ADR-0004 (ратифицирован Tech Lead
> 2026-09-28, вердикт в canon PR #2) кодифицируются здесь, а не
> переигрываются; дальнейшие изменения — только через SemVer-процесс (§7).
> Спека получает статус `stable` по факту первой конформной реализации в
> движке `vesma`.

Ключевые слова MUST / MUST NOT / SHOULD / MAY интерпретируются по
RFC 2119. Проза — русская; идентификаторы, имена примитивов и полей — EN
(канон экосистемы).

**Билингво-пара (обязательна).** Норматив — этот документ (RU); зеркало —
[spec.en.md](spec.en.md) (EN, информативное, single-commit sync); рядом —
[README.md](README.md) (EN quickstart интегратора). Правило i18n —
ADR-0001 §5.

## 1. Scope

decision-провайдер — сменная реализация типизированных точек решений
движка: судить релевантность записи, скорить качество по канону, выбирать
кандидата при дедупликации, отвечать на калиброванное «да/нет». Интерфейс
один — «семантический if»: на вход подготовленное canon-состояние, на
выходе типизированный ответ с калиброванной уверенностью и указанием, кто
ответил. Потребители программируются против интерфейса, а не против
конкретного провайдера: сегодня решают детерминированные эвристики
движка, завтра — локальная модель, когда-нибудь — внешний сервис, без
правок движка (домашний прецедент контрактной семьи — волна W5d: локальный
провайдер подключён поставкой артефакта и конфиг-флагом).

**В скоупе:**

- три примитива интерфейса: `Choice`, `Score`, `Noul` (§3.2);
- контрактные правила семейства: политика на стороне продукта, форма
  входа, приватность-гейт, калибровочный гейт (§3.3–§3.6);
- семейство реализаций и условия их включения: базовая детерминированная,
  локальная, внешняя (§3.7);
- семантика деградации fail-open и атрибуция ответов (§3.8–§3.9);
- классы отказов и реакция получателя (§4).

**Вне скоупа:**

- транспортная форма вызова и формат ответа — v1 фиксирует семантику, не
  провод; машинная схема появится отдельной минорной/мажорной версией
  контракта (§7);
- методология и артефакты калибровки — препегистрации, корпуса, пороги,
  вердикты прогонов, baseline-измерения — дом vesma-canon (доказательный
  слой); контракт фиксирует только гейт «калибровка до доверия» и
  указатель на методологию;
- конкретные вопросы, критерии `Choice` и шкалы `Score` — принадлежат
  продукту (код и конфиг движка), контрактом не фиксируются (§3.3);
- запуск/остановка/health провайдеров как процессов — дом
  `specs/service-lifecycle/v1`; провайдер — in-process интерфейс движка,
  а не компонент супервайзера (см. §3.10);
- цены, лимиты и пригодность внешних сервисов — разборы референсов
  остаются в canon.

**Потребители:** движок `vesma` (точки решений: guard-и дедупликации,
подсказки awareness, пороги качества), vesmaro-agent и будущие
потребители экосистемы, implementоры провайдеров (локальные модели,
адаптеры внешних сервисов).

### 1.1 Происхождение

Living-версия интерфейса мигрирована из vesma-canon ADR-0004
(2026-10-04, фаза 2 роадмапа vesma-specs); canon сохраняет историю и
указатель. Контрактно-пригодное перенесено: интерфейс и примитивы,
семейство реализаций, правила 1–4 ADR, семантика деградации fail-open
(прецедент CORTEX-E, волна W5d), телеметрия-атрибуция. Оставлено в canon:
экспериментальные вердикты (в том числе отклонённая калибровка W4c),
препегистрации и их аддендумы, корпуса и измерения, разбор цен внешнего
сервиса, секвенция волн. Аддендум W5a о локальной поверхности перенесён
по существу (ноль сети, гигиена экспорта датасета, fingerprint весов —
§3.7); его история остаётся в canon.

## 2. Терминология

Общие термины — [глоссарий](../../../GLOSSARY.md). Контрактные термины
этого документа:

| Термин | Значение |
|---|---|
| decision-провайдер | сменная реализация интерфейса «семантический if»: отвечает на типизированный вопрос продукта по подготовленному canon-состоянию |
| примитив решения | одна из трёх типизированных форм вопроса: `Choice`, `Score`, `Noul` |
| `Choice` | выбор варианта по заданным критериям → выбранный вариант + уверенность |
| `Score` | оценка на упорядоченной шкале → значение шкалы + уверенность |
| `Noul` | калиброванное «да/нет» → да/нет + уверенность |
| подготовленное canon-состояние | конверт + тело выбранных записей, собранное под конкретный запрос; единственная разрешённая форма входа провайдера |
| baseline-реализация (`deterministic`) | детерминированные эвристики движка, формализованные как первая реализация интерфейса; база калибровки и цель деградации |
| калибровка | проверка реализации по методологии canon (vitals): препегистрация, честный baseline, измерение на данных экосистемы; гейт участия в продуктовых решениях |
| уверенность (confidence) | число, имеющее смысл только у калиброванной реализации (§3.6) |
| fail-open деградация | требование семантики отказа: ошибка провайдера переключает работу на baseline и никогда не блокирует продуктовый путь (§3.8) |
| атрибуция | указание в каждом ответе и в журнале, кто ответил: примитив, реализация, уверенность (§3.9) |
| fingerprint весов | хэш артефакта локальной модели в отчёте прогона; смена весов = событие перекалибровки (§3.7) |
| приватность-гейт | единое для всех провайдеров правило: записи с тегом `no-federate` и записи с секретами не покидают хранилище (§3.5) |

## 3. Контракт

### 3.1 Единый интерфейс

- **MUST**: все типизированные точки решений движка программируются против
  интерфейса decision-провайдера, не против конкретной реализации.
- **MUST NOT**: потребители вызывать реализации напрямую в обход
  интерфейса; переключение провайдера — конфигурацией, без правок кода
  потребителей.
- **MUST**: каждый ответ несёт атрибуцию — кто ответил (реализация) —
  вместе с ответом (§3.9).

### 3.2 Примитивы

- **MUST**: интерфейс предоставлять ровно три примитива: `Choice`
  (выбор варианта → вариант + уверенность), `Score` (оценка на
  упорядоченной шкале → значение шкалы + уверенность), `Noul`
  (калиброванное «да/нет» → да/нет + уверенность).
- **MUST**: ответы типизированными — свободный текст ответом не является;
  реализация, способная отвечать только прозой, интерфейсу не соответствует.
- **MUST NOT**: провайдер генерировать и/или переписывать тела записей
  памяти; стилевой канон остаётся у людей и агентов (аддендум W5a,
  правило перенесено в §3.7).
- Новые примитивы — аддитивное изменение контракта (минорная версия, §7).

### 3.3 Политика живёт на уровне продукта

- **MUST**: вопросы, критерии `Choice` и шкалы `Score` фиксировать в коде
  и конфиге движка (продукт), а не в API провайдера.
- **MUST**: провайдер отвечать на заданный вопрос, а не изобретать, о чём
  спрашивать.
- **MUST**: смена провайдера не менять политику — вопросы, критерии и
  шкалы инвариантны к реализации.

### 3.4 Вход — только подготовленное canon-состояние

- **MUST**: входом провайдера быть подготовленное canon-состояние:
  конверт + тело выбранных записей, собранное под конкретный запрос.
- **MUST NOT**: передавать провайдеру сырые дампы памяти — никогда.
  Обоснование контрактно: дампы деградируют точность (context rot),
  открывают поверхность внедрения инструкций и раздули бы стоимость
  пересылки состояния.

### 3.5 Приватность-гейт единый для всех провайдеров

- **MUST**: записи с тегом `no-federate` и записи, содержащие секреты,
  никогда не покидать хранилище — для любой реализации, включая локальные
  (тег `no-federate` — правило хранения/федерации canon, силу сохраняет
  независимо от локальности провайдера).
- **MUST** (внешние вызовы): перед любым исходящим вызовом — обязательный
  механический скан подготавливаемого состояния на секреты и опасное
  содержимое; переиспользуются детекторы движка (`danger_detectors.detect`,
  `secrets_detector.detect_secrets`).
- **MUST**: находка любого класса останавливать вызов целиком, а не
  вырезать фрагмент.
- **SHOULD** (локальные реализации): скан секретов как гигиена экспорта
  датасета калибровки — датасет есть отдельная копия данных, записи с
  секретами и `no-federate` в него не попадают (процедура заморожена
  препегистрацией canon).

### 3.6 Калибровка обязательна до доверия

- **MUST NOT**: никакая реализация участвовать в продуктовых решениях до
  прохождения калибровки по методологии canon (vitals): препегистрация
  гипотезы и порогов до прогона, честный baseline против текущих
  эвристик, измерение на данных экосистемы. Методология и её артефакты —
  canon; контракт фиксирует гейт.
- **MUST**: локальность не давать льготы — «доверие без доказательств»
  запрещено одинаково для локальных и внешних провайдеров.
- **MUST**: «уверенность» некалиброванного провайдера не использоваться
  потребителями как число.
- **MUST**: калиброванный провайдер иметь смысл только там, где измеренно
  превосходит baseline-эвристику (условие превосходства на holdout — по
  замороженной препегистрации canon).

### 3.7 Семейство реализаций

| Реализация | Статус | Контрактные условия |
|---|---|---|
| (a) `deterministic` — детерминированные эвристики движка | база, работает с момента формализации | нулевая стоимость, ноль внешних вызовов; те же примитивы, детерминированные правила; baseline для калибровки (b)/(c) и цель деградации (§3.8) |
| (b) локальный роутер (семейство моделей `mnema`) | опциональная, за флагом | local-first: веса на машине, инференс и калибровка — **ноль сети**; провенанс — fingerprint весов в отчёте прогона; переобучение/смена весов = событие перекалибровки |
| (c) внешний адаптер (например Jev-семейство) | опциональная, **выключена по умолчанию навсегда** | двойной гейт включения: явный флаг владельца в конфиге **и** API-ключ; после включения действуют §3.4–§3.6 без исключений; состояние тарифицируется целиком за запрос (лимиты — разбор в canon) |

- **MUST**: дефолтной реализацией быть (a) `deterministic`; включение
  (b)/(c) — только явной конфигурацией.
- **MUST**: реализации (a) и (b) не иметь исходящего трафика — по
  построению; появление исходящего вызова из не-внешней реализации =
  дефект контракта (прецедент AST-tripwire на сетевые импорты в
  реализации движка, W5d).
- **MUST NOT**: гейт включения (c) обходиться одним из двух условий —
  флаг без ключа или ключ без флага не активируют адаптер.

### 3.8 Деградация fail-open

- **MUST**: любая ошибка провайдера деградировать к baseline:
  дефект загрузки/метаданных/пина артефакта — реализация целиком
  переключается на (a) `deterministic`; отказ инференса/схемы на
  конкретном запросе — одиночный вердикт деградирует к детерминированному
  правилу.
- **MUST NOT**: отказ провайдера блокировать продуктовый путь (инжест,
  дедупликацию, подсказки) — никогда.
- **MUST**: каждая деградация логироваться машинно-парсируемо, с кодом из
  пространства имён реализации (прецедент: `CORTEX-E-*` в реализации
  движка, W5d) и указанием действия (`provider-degraded` /
  `verdict-degraded` / `call-aborted`).
- **SHOULD**: дефект пина весов (fingerprint не совпал) трактоваться
  громко как событие перекалибровки — отказ загрузки с `code=`, не тихая
  подмена артефакта.

### 3.9 Телеметрия-атрибуция

- **MUST**: каждый ответ провайдера логироваться машино-парсируемо:
  примитив, реализация, уверенность — в ту же дисциплину структурных
  строк, что и телеметрия canon; это сырьё для строгого strict-дефолта.
- **MUST**: строка телеметрии позволять ответить на вопрос «кто принял
  это решение» без доступа к коду (атрибуция в данных, не в догадках).

### 3.10 Провайдер — не компонент супервайзера

- Decision-провайдер — in-process интерфейс движка, а не компонент
  экосистемы: манифест `specs/component-manifest/v1` на него не заводится,
  супервайзером не управляется. Смысловая семья — деградация вместо
  падения (философия тиров `specs/service-lifecycle/v1`): отказ провайдера
  снижает качество решений, но не роняет систему (§3.8).
- **MUST NOT**: выносить вызов провайдера на горячий путь как сетевой
  вызов к процессу-компоненту — интерфейс in-process; инлайн-вызовы
  внешних LLM в точках решений отвергнуты ADR-0004 (неконтролируемые цена
  и задержка, ответы свободным текстом, калибровка невозможна по
  построению).

### 3.11 Freeze форматов не задет

- **MUST**: интерфейс потреблять canon-записи как есть — конверт, типы и
  секции не меняются; схемы не правятся.
- **MUST NOT**: интерфейс требовать изменений формата хранения ради
  своего удобства.

## 4. Коды ошибок

Полный реестр кодов v1 не фиксируется: транспортная форма и формат ответа
в v1 не замораживаются (§7), а литеральные коды принадлежат пространствам
имён реализаций (прецедент — `CORTEX-E-*` движка). Контракт фиксирует
классы отказов и обязательное поведение получателя — реализация вправе
уточнять коды внутри класса, но не семантику:

| Класс отказа | Смысл | Источник | Обязательная реакция получателя |
|---|---|---|---|
| `<impl>-PIN` (класс) | дефект артефакта: fingerprint весов/метаданных/схемы не совпал с пином | загрузчик провайдера | полная деградация провайдера → (a) `deterministic`; громкий машинно-парсируемый warn; инжест не блокируется; событие перекалибровки |
| `<impl>-INFER` (класс) | отказ инференса или схемы ответа на конкретном запросе | исполнение провайдера | одиночный вердикт деградирует к детерминированному правилу; warn; ответ атрибутирован baseline-реализацией |
| `<impl>-GATE` (класс) | находка приватность-гейта перед внешним вызовом (секрет / опасное содержимое) | препроход скана | внешний вызов остановлен целиком; внешнего трафика нет; warn с действием `call-aborted` |
| `<impl>-CONFIG` (класс) | попытка включения с нарушением гейта (флаг без ключа, ключ без флага, неизвестное имя провайдера) | конфиг-загрузчик | конфигурация отклонена; активная реализация остаётся `deterministic`; warn |

## 6. Conformance

Исполняемый раннер `tools/conformance` валидирует декларации (манифесты,
JSON-схемы) — у этого контракта машинных деклараций v1 нет (§1, §7), поэтому
conformance-сьют v1 — человеческий чеклист интегратора
[conformance/checklist.md](conformance/checklist.md) (DP-01…DP-15), со
ссылками на разделы спеки и способами проверки. Исполняемый сьют появится
вместе с машинной формой интерфейса — отдельным минорным изменением
контракта; до этого зелёный чеклист + калибровочный отчёт canon — гейт
участия реализации в продуктовых решениях (§3.6).

## 7. Совместимость

- **SemVer**: `1.0.0-draft.1` → `1.0.0` по факту ратификации реализацией
  в движке vesma. Ломающее изменение = MAJOR + deprecation-окно
  `max(90 дней, 2 минорных релиза)` с dual-поддержкой (ADR-0001 §2);
  до 1.0 окно — 14 дней.
- **Аддитивное (минор)**: новые примитивы сверх трёх; машинная форма
  интерфейса (schema/ + исполняемый conformance-сьют); новые контрактные
  классы отказов.
- **Ломающее (MAJOR)**: изменение семантики примитивов, смена гейтов
  §3.5–§3.7, отказ от fail-open деградации.
- **Потребители**: движок `vesma` (точки решений), vesmaro-agent;
  семейство с соседями — манифест/супервайзер провайдера не касаются
  (§3.10), лэйаут не задействован (веса локальных моделей — артефакт
  пакета, дисциплина поставки — у движка).
- **Отложено за пределы v1 (осознанно)**: транспортная форма и схема
  вопроса/ответа; исполняемый conformance; подписи артефактов провайдеров
  (v1 даёт только fingerprint весов — прецедент пина в реализации движка);
  квоты/лимиты внешнего адаптера.

## 8. Threat model (мини-STRIDE)

Ассеты: содержимое хранилища памяти (в том числе `no-federate`/секреты),
типизированные вердикты, влияющие на продуктовые решения, целостность
весов локальных моделей. Границы: движок ↔ провайдер (in-process);
движок ↔ внешний сервис (только реализация (c), по умолчанию выключена);
движок ↔ данные калибровки (экспорт датасета).

| Категория | Угроза | Митигация | Проверка |
|---|---|---|---|
| **T**ampering | внедрение инструкций через вход провайдера | вход — только подготовленное canon-состояние (§3.4); сырые дампы запрещены; перед внешним вызовом — механический скан на опасное содержимое (§3.5) | DP-04, DP-05 |
| **T**ampering | тихая подмена весов локальной модели | fingerprint весов в отчёте прогона; несовпадение пина = громкий отказ загрузки + событие перекалибровки (§3.7, §3.8) | DP-12, DP-08 |
| **I**nformation Disclosure | утечка памяти через внешнего адаптера | приватность-гейт: `no-federate`/секреты не покидают хранилище (§3.5); скан перед каждым внешним вызовом, находка останавливает вызов целиком; дефолт — локальные реализации с нулём сети | DP-05, DP-11, DP-12 |
| **S**poofing | «кто на самом деле ответил?» — подмена источника вердикта | обязательная атрибуция каждого ответа и машинно-парсируемая телеметрия (§3.9) | DP-09 |
| **R**epudiation | «почему система так решила?» — решение неотслеживаемо | телеметрия решений в дисциплине canon: примитив, реализация, уверенность на каждый ответ (§3.9) | DP-09 |
| **D**enial of Service | отказ/зависание провайдера блокирует инжест и горячий путь | fail-open деградация: провайдер или одиночный вердикт переключается на baseline; продуктовый путь никогда не блокируется (§3.8); инлайн-внешние LLM на горячем пути отвергнуты (§3.10) | DP-07, DP-08 |
| **E**levation of Privilege | некалиброванный провайдер влияет на продуктовые решения | калибровочный гейт без льготы за локальность (§3.6); дефолт `deterministic`; не-базовые реализации — только за флагом; внешняя — флаг + ключ (§3.7) | DP-06, DP-10, DP-11 |

Каждая митигация закрыта пунктом чеклиста DP-01…DP-15 либо помечена
проверкой движка; тихих непроверяемых обещаний нет.

## 9. Миграция с легаси

Легаси здесь — точки решений движка до формализации интерфейса:
разрозненные эвристики, вызываемые напрямую в коде, и практика «модель в
проде без калибровки». Перенос — в движке; контракт фиксирует целевую
форму и порядок:

| Легаси-паттерн | Контрактный ответ |
|---|---|
| инлайн-эвристика в точке решения (dedup-guard, awareness-подсказка, порог качества) — вызов напрямую, без интерфейса | формализация как реализация (a) `deterministic` за интерфейсом (§3.7); потребитель программируется против примитива (§3.1) |
| «уверенность» непроверенной модели в продуктовом решении | калибровочный гейт §3.6: до калибровки — только baseline; уверенность некалиброванного числом не считается |
| внешний вызов в горячем пути без гейта | двойной гейт флаг+ключ (§3.7) + приватность-скан перед каждым вызовом (§3.5); по умолчанию — ноль внешних вызовов |
| молчаливый отказ модели (тихая деградация качества) | fail-open с громкой машинно-парсируемой деградацией (§3.8) — отказ виден, качество падает до baseline, а не в unknowable-зону |
| модель правит/переписывает тела записей | запрет §3.2: провайдер отвечает вердиктом, тела — у людей и агентов |

Порядок: формализация (a) за интерфейсом → телеметрия-атрибуция на всех
точках (§3.9) → калибровочный baseline (canon, методология vitals) →
подключение (b)/(c) за флагом с гейтами §3.6–§3.7 → вывод инлайн-паттернов
из оборота. Прецедент миграции — W5d: локальный провайдер подключён
поставкой артефакта и конфиг-флагом без правок движка.
